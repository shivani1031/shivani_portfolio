Build an MCP server in Python: a minimal guide

To build an MCP server in Python, install the official SDK with pip install "mcp[cli]", create an MCPServer, decorate a typed function with @mcp.tool() and call mcp.run(). The SDK turns the function's type hints and docstring into the tool's schema and description, and any MCP client can list and call it. You can test it in-process by passing the server object to the SDK's Client, with no model and no subprocess involved.

Before you start

This guide is the hands-on companion to two conceptual ones. Model Context Protocol for AI agents explains hosts, clients and servers and the security decisions that come with them. MCP vs function calling explains how the two layers relate. Here the focus is the server side only: writing one, seeing what it advertises and testing it.

The samples use version 2 of the official Python SDK, run against mcp 2.3.0. Version 2 renamed the main server class: the SDK's migration guide says FastMCP has become MCPServer, so tutorials that import FastMCP from mcp.server.fastmcp were written for version 1. Check which version you have installed before copying any example, including these.

Install the SDK with pip install "mcp[cli]" or uv add "mcp[cli]". The README notes that the cli extra adds the mcp command-line tool used later for the Inspector. Without it, the server still runs, but the command does not.

Step 1: write a server with one tool

The example exposes a single read-only tool that looks up a definition in a small glossary. It is deliberately trivial, so that everything on the page is about MCP rather than the lookup:

# Illustrative: a minimal MCP server exposing one read-only tool.
from mcp.server import MCPServer
from mcp.server.mcpserver.exceptions import ToolError

GLOSSARY = {
    "rag": "Retrieval-augmented generation: answering from retrieved text.",
    "mcp": "Model Context Protocol: a standard for connecting tools to AI apps.",
}

mcp = MCPServer("glossary")


@mcp.tool()
def define_term(term: str) -> str:
    """Look up a short definition of an AI term. Read-only."""
    key = term.strip().lower()
    if key not in GLOSSARY:
        raise ToolError(f"No definition for {term!r}. Known terms: {', '.join(sorted(GLOSSARY))}")
    return GLOSSARY[key]


if __name__ == "__main__":
    mcp.run()

Illustrative sketch, run against mcp 2.3.0. Replace the dictionary with your own data source.

Three things happen here. MCPServer("glossary") names the server, and clients see that name when they connect. The decorator registers define_term as a tool, using the function name as the tool name and the docstring as its description. And mcp.run() starts the server on the stdio transport, which is the default, so a client can launch it as a subprocess and talk to it over standard input and output.

Write the docstring for the model, not for a colleague. It is the text a model reads when deciding whether to call the tool, so say what the tool does, what it does not do, and that it is read-only.

Step 2: see what the server advertises

This is where an MCP server differs from a function you pass to a model API. With plain function calling, your application sends a fixed list of tool definitions with each request. With MCP, a client connects, initialises a session and asks the server what it offers with a tools/list request. The tool list is discovered at runtime, and the same server can be used by any client that speaks the protocol.

For the server above, the input schema the SDK generates from the type hint looks like this:

{'type': 'object', 'properties': {'term': {'title': 'Term', 'type': 'string'}}, 'required': ['term'], 'title': 'define_termArguments'}

That schema came entirely from term: str. Add a parameter with a default value and it appears as optional. Use a more specific type and the schema becomes more specific. The SDK validates incoming arguments against these hints before your function runs, so a call with a missing or wrongly typed argument fails without reaching your code.

Step 3: return errors the model can act on

When a tool fails, the result goes back to the model, which decides what to do next. A useful error says what went wrong and what would work instead. The SDK treats two kinds of exception differently:

  • ToolError, imported from mcp.server.mcpserver.exceptions, is for failures you expect. Its message is passed to the client in a result marked as an error, so the model can read it and try again.
  • Any other exception is treated as a crash. In the installed version, the client receives a generic "Error executing tool" message, and the exception's own text stays on the server.

That is why the sample raises ToolError with the list of known terms. In testing, raising a plain ValueError instead meant the client saw only the generic message, which gives a model nothing to work with. The split also protects you: unexpected errors can contain file paths, queries or other internal detail that should not reach a model or a user.

Step 4: test it in-process

The SDK's Client class accepts a URL, stdio launch parameters or, in tests, an MCPServer instance, which it connects to in-process. That makes a fast test possible with no model, no network and no subprocess:

# Illustrative: tests the server in-process, with no model and no subprocess.
import asyncio

from mcp import Client

from server import mcp


async def main():
    async with Client(mcp) as client:
        tools = await client.list_tools()
        assert [t.name for t in tools.tools] == ["define_term"]
        print(tools.tools[0].input_schema)

        ok = await client.call_tool("define_term", {"term": "RAG"})
        assert not ok.is_error
        print(ok.content[0].text)

        bad = await client.call_tool("define_term", {"term": "blockchain"})
        assert bad.is_error
        print(bad.content[0].text)


asyncio.run(main())

Illustrative sketch, run against mcp 2.3.0, where all three assertions passed.

The test checks the three things that break most often: the tool is listed under the expected name, a valid call succeeds and an invalid one returns an error result rather than raising. Add a check on the schema too, if clients depend on its exact shape. Once this passes, the same test can run in continuous integration with a normal test runner.

Step 5: try it with the Inspector

For manual exploration, the SDK README documents running uv run mcp dev server.py, which starts the server with the MCP Inspector, a browser-based tool for listing and calling tools by hand. It is a quick way to see what a client sees, including the descriptions and schema. It does not replace the automated test, because it checks one session by hand rather than every change.

After that, connect the server to a real MCP host. The configuration format differs from host to host, so follow that host's documentation. The final check is with a model in the loop: give it requests that should and should not trigger the tool, and confirm that it chooses correctly and passes sensible arguments.

Step 6: decide on the transport

The sample uses stdio, where the client launches the server as a local subprocess. That suits tools that run on the same machine as the host, such as a developer's desktop assistant. To serve the tool over the network, the README shows running the server with the streamable-http transport instead, and mcp.run accepts it as an option. A network transport changes the security picture: anyone who can reach the URL can try to call your tools, so authentication and authorisation move from optional to essential. The SDK includes options for both, and the MCP overview guide covers what to decide before exposing a server.

Is MCP just tool calling, then?

Looking at the server makes the difference concrete. The function you wrote is ordinary Python, and on the model side it ends up as a tool call, just as it would with function calling. What MCP adds is the layer in between: a standard way for a client to discover the tool at runtime, a schema generated from your code and a server that any compatible host can launch or connect to. The model never sees MCP itself. It sees tool definitions supplied by its host, and the host gets those definitions from your server.

So if one application owns the tool and only one model calls it, function calling alone is simpler. Build an MCP server when the same tools should be usable from several hosts, or by other teams, without each of them rewriting the integration.

Common mistakes

  • Copying version 1 imports. FastMCP examples need adapting for version 2.
  • Printing to standard output. On the stdio transport, standard output carries protocol messages, so stray prints can corrupt them. Log to standard error instead.
  • Vague docstrings. The model chooses tools from their descriptions.
  • Raising generic exceptions for expected failures. Use ToolError so that the model sees a useful message.
  • Giving a tool more access than it needs. Start read-only and add write tools deliberately.

Frequently asked questions

What is the difference between MCP and tool calling?

Tool calling is how a model asks the application to run a function. MCP is a protocol between the application and a server that supplies tools, so they can be discovered at runtime and reused by any compatible host. The two work together.

Should I use FastMCP or MCPServer?

In version 2 of the official Python SDK, the migration guide says FastMCP was renamed MCPServer. Use whichever matches the SDK version you have installed, and check imports against that version's documentation.

How do I test an MCP server without a model?

Pass the server object to the SDK's Client class, which connects in-process. You can then list tools and call them with valid and invalid arguments in an ordinary automated test.

Do I need the mcp[cli] extra?

Only for the mcp command-line tool, which runs the Inspector and other development commands. The server itself runs with the plain mcp package.
