LangGraph human-in-the-loop with interrupt: approve, edit or reject

To add human approval in LangGraph, call interrupt() inside a review node with the proposed action as its payload, compile the graph with a checkpointer, and run it with a thread_id in the config. The run pauses and saves its state. When the reviewer decides, invoke the graph again with Command(resume=decision) and the same thread ID: interrupt() returns the decision, and the node routes to execute the original, execute an edited version, or stop.

What this guide adds

Two earlier guides cover the ground around this one. Human-in-the-loop approval for AI agents explains which actions deserve a pause and how to design the review step, independent of any framework. LangGraph examples includes a minimal pause that resumes with a yes or no. This guide goes further on the LangGraph side: a structured decision with three outcomes, routing with Command, finding paused threads, validating the reviewer's answer, and the rules that cause subtle bugs.

The code was run against the langgraph 1.2 Python package and checked against the LangGraph interrupts documentation and the docstrings in the installed package. LangGraph has changed its human-in-the-loop API before, so compare these details with the version you have installed.

The three pieces you need

  • interrupt(value). Called inside a node, it stops the run and surfaces value to the caller. The value should be JSON-serialisable: the proposal, a question and the allowed options work well.
  • A checkpointer. Pausing only works if the graph's state is saved somewhere. Pass one to compile(checkpointer=...). InMemorySaver is fine for tests but is lost when the process stops, so production needs a database-backed checkpointer.
  • A thread ID. Every run goes in config["configurable"]["thread_id"]. The checkpoint is stored under that ID, and resuming needs the same ID. A new ID starts an empty thread rather than continuing the paused one.

Resuming uses Command(resume=...) as the input to invoke or stream. Whatever you put in resume becomes the return value of interrupt() inside the node.

A complete approve, edit or reject example

The sample below is illustrative and runs as written. A fixed proposal stands in for a model call, and the execute node only builds a string, so nothing is refunded. It runs three threads, one for each decision.

# Illustrative only. propose stands in for a model call; nothing is paid.
from typing import Literal, TypedDict

from langgraph.checkpoint.memory import InMemorySaver
from langgraph.graph import END, START, StateGraph
from langgraph.types import Command, interrupt


class State(TypedDict, total=False):
    ticket: str
    proposal: dict
    decision: str
    note: str
    result: str


def propose(state: State):
    # In a real graph a model drafts this proposal; here it is fixed.
    return {"proposal": {"action": "refund", "order": "A-1001", "amount": 40}}


def review(state: State) -> Command[Literal["execute", "rejected"]]:
    # Code above interrupt() runs again on resume, so keep it free of side effects.
    answer = interrupt({
        "kind": "approval",
        "proposal": state["proposal"],
        "options": ["approve", "edit", "reject"],
    })
    choice = answer.get("decision")
    if choice == "approve":
        return Command(goto="execute", update={"decision": "approve"})
    if choice == "edit":
        edited = {**state["proposal"], **answer.get("changes", {})}
        return Command(goto="execute", update={"decision": "edit", "proposal": edited})
    return Command(goto="rejected",
                   update={"decision": "reject", "note": answer.get("reason", "")})


def execute(state: State):
    p = state["proposal"]
    # A real call should send an idempotency key, such as the thread ID.
    return {"result": f"refunded {p['amount']} on {p['order']}"}


def rejected(state: State):
    return {"result": "not run: " + (state.get("note") or "no reason given")}


builder = StateGraph(State)
builder.add_node("propose", propose)
builder.add_node("review", review)
builder.add_node("execute", execute)
builder.add_node("rejected", rejected)
builder.add_edge(START, "propose")
builder.add_edge("propose", "review")
builder.add_edge("execute", END)
builder.add_edge("rejected", END)
graph = builder.compile(checkpointer=InMemorySaver())


def run_case(thread_id, human_answer):
    config = {"configurable": {"thread_id": thread_id}}
    graph.invoke({"ticket": "Customer asks for a refund"}, config)

    snapshot = graph.get_state(config)
    pending = snapshot.interrupts[0]
    print(thread_id, "paused before", snapshot.next, pending.value["proposal"])

    final = graph.invoke(Command(resume=human_answer), config)
    print(thread_id, final["decision"], "|", final["result"])


run_case("ticket-1", {"decision": "approve"})
run_case("ticket-2", {"decision": "edit", "changes": {"amount": 25}})
run_case("ticket-3", {"decision": "reject", "reason": "outside the refund window"})

Running it prints a pause for each thread, followed by an approved refund of 40, an edited refund of 25, and a rejection that records the reason. The interesting parts are the review node and the resume value.

Routing the decision with Command

Command appears in two roles here, and it helps to keep them apart. As the input to invoke, Command(resume=...) carries the human's answer back into the paused node. As the return value of a node, Command(goto=..., update=...) updates state and chooses the next node in one step, which replaces a separate conditional edge.

The return annotation Command[Literal["execute", "rejected"]] declares which nodes the review node can reach, so that LangGraph can show those routes when it draws the graph.

Notice the default. Anything other than approve or edit goes to rejected. A typo, a missing field or an unexpected value should never execute an action, so make "do not run" the fallback.

Handling edits safely

An edit is the most useful option and the easiest to get wrong. In the example, the reviewer sends only the fields they changed, and the node merges them into the original proposal. In a real system, limit which fields can be edited, validate the merged result with the same checks that the agent's proposal passed, and keep both versions in state so that your logs show what the agent proposed and what was approved.

If an edit changes the action enough to need a second look, for example a much larger amount, route back to the review node instead of to execution. Because the node is called again on a new step, it raises a fresh interrupt for the new proposal.

Finding paused threads

A reviewer works from a list, not a terminal. Two tools help to build one:

  • The result of invoke contains an __interrupt__ key when the run paused, holding the interrupt objects and their values.
  • graph.get_state(config) returns a snapshot for a thread. snapshot.next shows the node waiting to run, and snapshot.interrupts lists pending interrupts, each with a value and an id.

Checkpointers are not a work queue, so record each pause in your own table as well: the thread ID, the payload, who should review it and when it was created. Your review screen reads that table, and the decision handler resumes the matching thread. The guide on building a backend API for an AI agent shows how to wrap runs in endpoints.

Rules that cause subtle bugs

The LangGraph documentation lists several rules for interrupts. These are the ones most likely to bite:

  • The node runs again from the start. On resume, LangGraph re-executes the interrupted node from its first line, and interrupt() then returns the resume value instead of pausing. Code before the call runs twice, so keep it free of side effects. Never send the email and then ask for approval in the same node.
  • Do not catch the pause. interrupt() works by raising an exception. A bare try and except around it swallows the pause. Catch specific exception types, or keep the call outside the try block.
  • Keep the order stable. When a node calls interrupt() more than once, resume values are matched by position. Do not skip interrupts conditionally or loop over data that might change between runs.
  • Several pauses at once. If parallel branches interrupt together, resume with a dictionary that maps each interrupt's ID to its value.
  • Make execution idempotent. A retry or a duplicate resume should not repeat a refund. Pass an idempotency key, such as the thread ID plus the proposal, to the system that performs the action.

Validating the reviewer's answer

The resume value comes from outside the graph, so treat it as untrusted input. Check that the person resuming is allowed to approve this kind of action before you call invoke, and validate the shape of the decision.

Recent versions add a response_schema argument to interrupt(). The documentation states that it needs langgraph 1.2.12 or later. Given a Pydantic model, TypedDict or dataclass, it publishes a JSON Schema for the client and validates the resume value, returning the validated object. On older versions, validate the decision yourself at the start of the review node or in the API handler.

Going to production

Swap InMemorySaver for a durable checkpointer, give every run a meaningful thread ID such as a ticket number, and decide what happens when nobody answers. Reminders, escalation, expiry and audit logs are organisational choices as much as code, and approval workflows for AI agents in production covers how to design them. Test each route with a fixed proposal and scripted decisions, as the example does; testing AI agents has more on testing without a live model.

Frequently asked questions

How does interrupt work in LangGraph?

Calling interrupt inside a node stops the run, saves the state through the checkpointer and returns the value you passed to the caller. When you invoke the graph again with Command(resume=...) and the same thread ID, the node runs again and interrupt returns the resume value.

Why does my LangGraph interrupt not pause?

The usual causes are compiling the graph without a checkpointer, not passing a thread_id in the config, or wrapping interrupt in a broad try and except block that catches the exception it uses to pause.

How do I resume a LangGraph graph after an interrupt?

Call invoke or stream with Command(resume=value) as the input and the same config, including the same thread ID. The value becomes the return value of interrupt in the paused node.

Can a reviewer edit the agent's proposal?

Yes. Resume with the changed fields, merge them into the proposal inside the review node, validate the result and route to execution. Keep the original as well, so that you can see what was changed.

Which checkpointer should I use for human approval in production?

Use a durable, database-backed checkpointer rather than InMemorySaver, because a person may answer hours or days later, after the process has restarted.
