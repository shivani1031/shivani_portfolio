LangGraph state explained: schemas, reducers and updates

In LangGraph, state is the shared data that flows through a graph. You declare its shape with a state schema, usually a TypedDict; each node receives the current state and returns only the keys it wants to change; and LangGraph merges each returned key into the state using that key's reducer, or simply replaces the value if the key has no reducer. Getting reducers right is what makes lists accumulate, chat histories merge and parallel branches combine without errors.

State, nodes and edges

LangGraph is usually explained through three ideas: state, nodes and edges. Edges decide which node runs next, and nodes do the work. State is what connects them: it is the only thing a node sees, and the only thing it can change. If you have already built a first graph with the LangGraph tutorial for beginners, you have used state without needing to think much about it. This guide looks at how updates are actually applied, which is where most confusing bugs come from.

Everything here was checked against the installed langgraph Python package, version 1.2, and its source. The samples are illustrative, run as written, and use plain functions instead of model calls.

The state schema

The schema is the class you pass to StateGraph. A TypedDict is the common choice; a dataclass or a Pydantic model also works, with Pydantic adding validation at run time at some cost in speed. Each key in the schema becomes a separate channel inside the graph, and each channel has its own rule for combining updates.

A key's rule comes from its type annotation. A plain type, such as topic: str, means "last value wins". A type wrapped in Annotated with a function, such as Annotated[list[str], operator.add], means "combine the old value and the update with this function". That function is the reducer. It receives the current value and the update, and returns the new value.

StateGraph also accepts separate input_schema and output_schema arguments, so callers can provide fewer keys than the graph uses internally and receive only the keys they need. A separate context_schema holds run-time settings, such as a user id or model name, that are not part of the state and are not updated by nodes.

Nodes return partial updates

A node returns a dictionary containing only the keys it changed. It does not return the whole state, and it should not modify the state it was given. LangGraph collects the update, runs each key through its reducer, and the merged result is what the next node receives.

Partial updates are what make parallel branches possible. When two nodes run in the same step, each returns its own small update, and the reducers decide how they combine. The sample below fans out to two search nodes that both write to notes, then joins them in a summary node:

# Illustrative only. Plain functions stand in for model calls.
import operator
from typing import Annotated
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END


class ResearchState(TypedDict):
    topic: str                                   # no reducer: last write wins
    notes: Annotated[list[str], operator.add]    # reducer: lists are concatenated
    summary: str


def search_web(state: ResearchState) -> dict:
    return {"notes": [f"web result about {state['topic']}"]}


def search_docs(state: ResearchState) -> dict:
    return {"notes": [f"internal doc about {state['topic']}"]}


def summarise(state: ResearchState) -> dict:
    return {"summary": f"{len(state['notes'])} notes on {state['topic']}"}


builder = StateGraph(ResearchState)
builder.add_node("search_web", search_web)
builder.add_node("search_docs", search_docs)
builder.add_node("summarise", summarise)
builder.add_edge(START, "search_web")
builder.add_edge(START, "search_docs")          # both run in the same step
builder.add_edge(["search_web", "search_docs"], "summarise")
builder.add_edge("summarise", END)
graph = builder.compile()

result = graph.invoke({"topic": "vector databases", "notes": []})
print(sorted(result["notes"]))
print(result["summary"])

It prints both notes and then 2 notes on vector databases. Because notes has the operator.add reducer, the two lists are concatenated. The order in which parallel updates are applied is not something to rely on, which is why the sample sorts before printing.

What happens without a reducer

Remove the reducer and the same fan-out fails. A key with no reducer can receive only one value per step, because LangGraph has no rule for choosing between two. This sample has two parallel nodes writing a plain note key:

# Illustrative only. Shows the error when two parallel nodes write a key with no reducer.
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.errors import InvalidUpdateError


class State(TypedDict):
    topic: str
    note: str   # no reducer


builder = StateGraph(State)
builder.add_node("a", lambda s: {"note": "from a"})
builder.add_node("b", lambda s: {"note": "from b"})
builder.add_edge(START, "a")
builder.add_edge(START, "b")
builder.add_edge(["a", "b"], END)
graph = builder.compile()

try:
    graph.invoke({"topic": "x"})
except InvalidUpdateError as err:
    print("InvalidUpdateError:", str(err).splitlines()[0])

It raises InvalidUpdateError with the message that the key can receive only one value per step, and suggests using an annotated key. The fix is to give the key a reducer, or to have each branch write to its own key. In a sequential graph the same plain key works fine, because only one node writes to it at a time.

Messages state and add_messages

Chat applications keep a list of messages in state, and appending with operator.add is not quite enough: sometimes you need to replace or delete a message. LangGraph provides the add_messages reducer for this. It appends new messages, replaces any message whose id matches an existing one, and deletes messages when given a RemoveMessage with that id. It also converts plain dictionaries and tuples into message objects.

MessagesState is a ready-made schema with a single messages key that uses add_messages. You can extend it with your own keys:

# Illustrative only. A stub replaces the chat model.
from langchain_core.messages import AIMessage, HumanMessage, RemoveMessage
from langgraph.graph import StateGraph, MessagesState, START, END
from langgraph.graph.message import add_messages


class ChatState(MessagesState):
    turns: int


def fake_model(state: ChatState) -> dict:
    last = state["messages"][-1].content
    return {"messages": [AIMessage(content=f"You said: {last}")],
            "turns": state.get("turns", 0) + 1}


builder = StateGraph(ChatState)
builder.add_node("model", fake_model)
builder.add_edge(START, "model")
builder.add_edge("model", END)
graph = builder.compile()

out = graph.invoke({"messages": [HumanMessage(content="hello", id="m1")], "turns": 0})
for m in out["messages"]:
    print(type(m).__name__, "|", m.content)
print("turns:", out["turns"])

# The reducer on its own: same id replaces, RemoveMessage deletes.
history = [HumanMessage(content="hi", id="m1"), AIMessage(content="draft", id="m2")]
history = add_messages(history, [AIMessage(content="final", id="m2")])
print([m.content for m in history])
history = add_messages(history, [RemoveMessage(id="m1")])
print([m.content for m in history])

The graph prints the human and AI messages and a turn count of one. The second half calls the reducer directly: sending a message with id m2 replaces the draft, and RemoveMessage(id="m1") removes the first message, leaving only final. Trimming old messages this way is one approach to keeping a long conversation within the model's context.

Bypassing a reducer with Overwrite

Occasionally a node needs to replace a value that normally accumulates, for example to reset a list of notes. Recent versions provide Overwrite in langgraph.types: returning {"notes": Overwrite(["fresh start"])} writes the value directly instead of passing it through the reducer. Two Overwrite updates to the same key in one step raise an error, for the same reason as above. If your version does not have it, a custom reducer that treats a special value as "reset" achieves the same thing.

Designing a good state

  • Keep it small and explicit. Store what nodes need to make decisions: inputs, intermediate results, counters and flags. Large documents can live elsewhere, with an id in state.
  • Choose reducers deliberately. For each key, ask whether more than one node can write it, and whether values should replace or accumulate.
  • Use counters for loops. A retry or step count in state lets a router stop a loop, in addition to LangGraph's own recursion limit.
  • Keep state serialisable. With a checkpointer, state is saved after each step. Clients, connections and open files belong in context or in the node's code, not in state.
  • Separate run state from long-term memory. State and checkpoints hold what a single conversation or task needs. Facts that should outlast it belong in a store, as described in agent memory: short-term and long-term state.

Common mistakes

  • Returning the whole state from every node. With reducers, this duplicates data: a node that returns the full notes list under operator.add doubles it.
  • Mutating the input state. Changing state["notes"] in place is not recorded as an update and can behave unpredictably with checkpoints. Return a new value.
  • Forgetting the reducer on a list. Without one, each update replaces the list, so earlier items disappear silently in a sequential graph and fail loudly in a parallel one.
  • Reading a key that was never set. A TypedDict key has no default. Provide it in the input or read it with state.get.
  • Messages without ids. add_messages assigns ids to new messages, but if you build your own replacement message without the original id, it is appended instead of replacing.

Frequently asked questions

What is state in LangGraph?

State is the shared data that flows through a graph. You define its keys in a schema, nodes read it and return partial updates, and LangGraph merges those updates using each key's reducer before the next node runs.

What is a reducer in LangGraph?

A reducer is a function attached to a state key with Annotated. It takes the current value and an update and returns the new value, for example operator.add to join lists. Keys without a reducer keep the latest value.

Why do I get InvalidUpdateError in LangGraph?

Usually because two nodes running in the same step wrote to a key that has no reducer. Add a reducer to that key, or have each parallel branch write to a different key.

What does add_messages do?

It is the reducer used by MessagesState. It appends new messages, replaces a message that has the same id as an existing one, and removes a message when it receives RemoveMessage with that id.
