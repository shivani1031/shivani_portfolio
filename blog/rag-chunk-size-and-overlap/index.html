RAG chunk size and overlap: how to choose

Choose chunk size by working out the range your embedding model, context budget and documents allow, then testing a few sizes within it on your own questions. Treat overlap as a small fraction of the chunk, often zero for cleanly structured text, and keep it only if your test shows answers being lost at boundaries.

Why there is no single right number

Chunk size settles how much text each retrievable unit holds. Overlap settles how much text neighbouring chunks share. Both affect whether the passage that answers a question can be found, and whether it reaches the model complete.

Recommended values circulate widely, but they were measured on someone else's documents and questions. A size that suits short help articles can split a contract clause in half, and a size that suits long reports can bury a one-line answer among unrelated text. The useful skill is not knowing a number but knowing how to find yours.

This guide assumes you have already chosen a splitting method. If not, read choosing chunking strategies for RAG first, which compares fixed, recursive, structure-aware, semantic and parent-child chunking. Here the focus is narrower: the two numbers, and how to test them.

Step 1: measure in tokens

Embedding models and LLMs limit their input in tokens, not characters or words, and the ratio between them varies by language and content. Code, tables and non-English text often use more tokens per word than plain English prose. If you set sizes in characters, some chunks may be far larger in tokens than you expect.

Count with the tokeniser that matches your embedding model where you can. If that is not available, measure a sample of your own documents to find the real ratio rather than relying on a rule of thumb.

Step 2: find the limits that set the range

Before testing anything, three constraints narrow the range of sensible sizes.

The embedding model's input limit

Every embedding model has a maximum input length. Text beyond it may be truncated without warning or rejected, depending on the provider. Your largest chunk, including any title or heading text you prepend, must fit. Check the limit in the model's own documentation. Even well below the limit, very long inputs produce a single vector that has to represent several ideas at once, which can make specific questions harder to match.

The context budget

What reaches the model is roughly the chunk size multiplied by the number of chunks you retrieve, plus instructions, conversation history and room for the answer. If you plan to pass eight chunks, each chunk can be far smaller than if you pass three. Work this out from the other direction too: decide how many passages a typical answer needs, and how much context you are willing to pay for on every request.

The shape of the answers

Look at where answers sit in your documents. If most answers are a sentence or two, such as a deadline or a limit, smaller chunks match them more precisely. If answers are procedures or explanations that run for several paragraphs, chunks need to be large enough to hold them, or you need a parent-child arrangement that retrieves small pieces and returns their surrounding section.

Step 3: decide what overlap is for

Overlap exists to protect information that falls across a boundary. If a sentence starts at the end of one chunk and finishes at the start of the next, neither chunk contains it whole. Repeating some text in both chunks makes it more likely that one of them does.

That benefit has costs:

  • More chunks. With a chunk size of 400 tokens and an overlap of 100, each new chunk advances only 300 tokens, so the index holds about a third more chunks than with no overlap. Embedding and storage grow accordingly.
  • Near-duplicate results. Adjacent chunks share text, so they often both match the same question and take two of your limited result slots with largely the same content.
  • Repeated context. If both are passed to the model, you pay for the shared text twice.

Overlap matters most when splitting ignores structure, as fixed-size splitting does. When chunks already follow paragraphs, sections or clauses, boundaries tend to fall where ideas end, and overlap adds less. In that case, start at zero and add it only if your test shows answers being cut.

Here is a minimal token-based splitter that makes the relationship between the two settings explicit:

def chunk_tokens(tokens, size, overlap):
    if not 0 <= overlap < size:
        raise ValueError("overlap must be at least 0 and smaller than size")
    step = size - overlap
    chunks = []
    for start in range(0, len(tokens), step):
        chunks.append(tokens[start:start + size])
        if start + size >= len(tokens):
            break
    return chunks

Illustrative sketch. It works on a list of tokens and ignores sentence and section boundaries.

The step between chunk starts is the size minus the overlap, which is why an overlap equal to or larger than the size is rejected: the splitter would never move forward.

Step 4: build a test that checks the span

A common retrieval test checks whether the right document or chunk appears in the top results. For tuning size and overlap, a stricter check is more informative: does a retrieved chunk contain the whole answer?

To set it up, collect realistic questions and, for each one, copy the shortest piece of text that fully answers it. Store that answer span as text rather than as a chunk ID, because IDs change every time you rechunk. Include questions whose answers sit near headings, inside lists and across paragraph breaks, since those are the cases that size and overlap affect.

The test then asks, for every configuration, how often a top result contains the answer span in full. That catches the failure that matters here, where retrieval finds the right area but the answer has been cut in two.

Step 5: run a small sweep

With the test in place, try a few sizes within your range and a few overlap values for each, rebuilding the index every time:

def sweep(documents, questions, build_index, search, k=5):
    results = []
    for size in (200, 400, 800):
        for overlap in (0, size // 10, size // 5):
            index = build_index(documents, size=size, overlap=overlap)
            contained = 0
            for q in questions:
                top = search(index, q["text"], k=k)
                if any(q["answer_span"] in chunk for chunk in top):
                    contained += 1
            results.append({
                "size": size,
                "overlap": overlap,
                "span_recall": contained / len(questions),
                "chunks": len(index),
            })
    return results

Illustrative sketch. build_index and search are placeholders for your own pipeline, and the sizes are examples rather than recommendations.

A few rules keep the sweep honest:

  • Change only size and overlap. Keep the embedding model, retrieval method and number of results fixed, or you will not know what caused a difference.
  • Compare at the number of results you will use. A configuration that wins at ten results may lose at three.
  • Record the cost. Note the number of chunks and the context each configuration sends, not just its score.
  • Use enough questions. With a small set, a difference of one or two questions can be noise. Look at which questions changed, not only the totals.

Step 6: read the results

Numbers tell you which configuration won; the failures tell you why. For questions that fail, look at what was retrieved:

  • The answer is split across two chunks. Overlap may help, but a structure-aware split that respects the boundary is often a cleaner fix.
  • The right chunk is found but ranks low. The chunk may be too large and mixed. Try a smaller size, or add a reranker.
  • The chunk matches but lacks context. A passage such as "this applies to both plans" needs the heading above it. Prepending the title and section path often helps more than a larger size.
  • Several near-identical chunks fill the results. Reduce overlap, or remove duplicates after retrieval.

Often the best configuration is not the top scorer but the cheapest one that is close to it. A small gain that doubles the context sent on every request may not be worth having.

Content that needs its own settings

One size rarely suits a mixed collection. FAQ pages, where each answer is short and self-contained, often work best with one question and answer per chunk regardless of length. Long policies and manuals may need larger chunks or parent-child retrieval. Tables need their headers kept with every row group. If your collection mixes these types, it is reasonable to chunk each type differently and record the settings in each chunk's metadata.

When to test again

Size and overlap are tied to the rest of the pipeline. Rerun the sweep when you change the embedding model, since input limits and behaviour differ; when you add a reranker, which can make larger candidate sets workable; and when your content changes character, such as adding a new document type. Because rechunking means re-embedding, build ingestion so that a new index can be built and compared alongside the old one before switching.

Once retrieval looks right, confirm that final answers improved as well, using the approach in how to evaluate a RAG system. For help tuning retrieval on your own documents, see RAG development.

Frequently asked questions

What is a good default chunk size for RAG?

There is no default that suits every corpus. Work out the range your embedding model's input limit and your context budget allow, start in the middle of it and test a smaller and a larger size on your own questions.

Is chunk overlap always needed?

No. Overlap mainly helps when splitting ignores structure. If chunks already follow paragraphs or sections, start without it and add a small amount only if testing shows answers being cut at boundaries.

How much overlap should I use?

A small fraction of the chunk size is a common starting point. Larger overlap adds chunks, storage and near-duplicate results, so compare a few values in a sweep rather than picking one by habit.

Should chunk size be measured in characters or tokens?

Tokens, because embedding models and LLMs limit their input in tokens. The ratio of characters to tokens varies with language and content, so a size set in characters can exceed a model's limit.
