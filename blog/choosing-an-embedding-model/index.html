How to choose an embedding model

Choose an embedding model in two passes. First rule out models that fail your hard constraints, such as language, input length, data handling and licence. Then compare the remaining few on a labelled set of your own questions, broken down by question type, and pick the cheapest model that is not meaningfully worse.

Why the choice deserves a method

The embedding model decides which passages a RAG system can find. If it places a question far from the passage that answers it, no amount of prompt work will recover the answer. It is also expensive to change later, because every stored vector has to be regenerated with the new model.

Public leaderboards are a reasonable place to find candidates, but they measure performance on general test sets. Your users' wording, your domain's vocabulary and your mix of languages may look nothing like those sets. This guide sets out a selection process: what to rule out first, how to build a comparison that reflects your use, and how to make the final call.

For the basics of what embeddings are, and for choosing where to store them, see embeddings and choosing a vector database.

Pass one: rule out on hard constraints

Some requirements are not trade-offs. A model that fails one is out, however well it scores. Write these down before looking at any results:

  • Languages. List every language your documents and users use. If someone may ask in one language about a document in another, the model must handle cross-language matching, not just each language separately.
  • Data handling. Decide whether your text may be sent to a third-party API at all, and if so, under what terms and in which regions. If it may not, only models you can run yourself remain.
  • Licence. For self-hosted models, read the licence. Some restrict commercial use or impose conditions.
  • Input length. The maximum input must cover your largest chunk plus any heading text you prepend. Check whether longer input is cut off silently or rejected.
  • Infrastructure. If you will run the model yourself, confirm it fits the hardware you have and can embed your full collection in an acceptable time.
  • Retirement policy. For hosted models, find out how much notice the provider gives before retiring a model, since retirement forces a full re-embed.

Aim to finish this pass with three or four candidates. Comparing more than that takes time without adding much.

Pass two: build a test set that reflects your use

The comparison is only as good as its questions. Gather them from where real questions already appear: support emails, search logs, chat transcripts or the questions staff answer most often. Keep the original wording, including vague and misspelt questions, because those are where models differ.

For each question, record which chunks genuinely help answer it. Then tag every question with a group that describes its type. The groups are what make this method more useful than a single score. Useful groups often include:

  • Paraphrase. The user's words differ from the document's, such as "cancel" against "terminate".
  • Exact terms. Product codes, error messages, names and acronyms.
  • Cross-language. A question in one language whose answer is in another.
  • Negation and conditions. Questions that hinge on "not", "except" or "only if".
  • Unanswerable. Questions your content does not answer, to see what each model returns instead.

Also add hard negatives to the collection: passages that look relevant but are wrong, such as last year's policy or a similar product's manual. A model that ranks these above the right passage will cause confidently wrong answers in production.

Running the comparison

Use the same chunks for every model, and change nothing else. The function below scores one model, reporting recall and mean reciprocal rank separately for each group of questions:

from collections import defaultdict

def evaluate(model_name, embed_query, embed_doc, chunks, questions, k=5):
    doc_vecs = {cid: embed_doc(text) for cid, text in chunks.items()}
    by_group = defaultdict(lambda: {"hits": 0, "rr": 0.0, "n": 0})
    for q in questions:
        qv = embed_query(q["text"])
        ranked = sorted(
            doc_vecs,
            key=lambda cid: sum(a * b for a, b in zip(qv, doc_vecs[cid])),
            reverse=True,
        )[:k]
        g = by_group[q["group"]]
        g["n"] += 1
        for rank, cid in enumerate(ranked, start=1):
            if cid in q["relevant"]:
                g["hits"] += 1
                g["rr"] += 1 / rank
                break
    return {
        group: {"recall": v["hits"] / v["n"], "mrr": v["rr"] / v["n"]}
        for group, v in by_group.items()
    }

Illustrative sketch. embed_query and embed_doc are placeholders returning normalised vectors, and exact search is used because the test set is small.

Recall shows how often a helpful chunk appears in the top results. Mean reciprocal rank shows how high it appears, which matters when only the first few results reach the model. Set k to the number of results your pipeline actually passes on.

The function takes separate query and document embedding functions on purpose. Some models are trained to treat questions and passages differently, through a prefix, an instruction or a setting, and their documentation says which to use. Applying the wrong one, or none, can quietly lower quality, so set this up correctly for each candidate before comparing.

Checks beyond the main score

Reduced dimensions

Some models can produce shorter vectors, either through a setting or by truncating the output, when they were trained to support it. Shorter vectors use less storage and memory and can speed up search. If a candidate offers this, run the test again at the reduced size and see whether any group drops noticeably. Only truncate a model whose documentation says it supports truncation.

Score distributions

If you plan to use a similarity threshold, for example to decide when nothing relevant was found, look at the scores each model gives to the right passages and to unanswerable questions. With some models the two ranges overlap so much that no threshold separates them. Thresholds do not transfer between models, so a value tuned for one is meaningless for another.

Speed and throughput

Measure how long query embedding takes from your own servers, since it adds to every request. Measure separately how long it takes to embed the whole collection, which matters for the first build and for every future re-embed.

Making the decision

Put the results in one table: a row per model, with recall and rank for each group, plus dimensions, query latency, full-collection embedding time and running cost. Then work through it in order:

  1. Remove any model that does badly on a group that matters to you, even if its average is high.
  2. Among the rest, look at the size of the differences. If two models differ by a question or two on a small set, treat them as equal.
  3. Choose the simplest and cheapest of the models that remain, weighing hosting, operations and retirement risk.

Read the failures before you finish. If every model fails on exact codes, the fix is probably hybrid search and reranking, not a different embedding model. If they all fail on questions whose answers are split across chunks, revisit chunk size first; RAG chunk size and overlap explains how to test it.

Planning for the next change

The model you choose today will probably not be the one you use in a few years. Make the next change routine rather than an emergency. Keep the test set and the scoring script in your repository. Store the model name and version with every vector. Build ingestion so that a second index can be filled with a new model, scored with the same test and switched over only when it wins.

Once retrieval is settled, check the final answers too, using the approach in how to evaluate a RAG system. If you would like help choosing and testing a model on your own content, see RAG development.

Frequently asked questions

Can I rely on public embedding leaderboards?

Use them to find candidates, not to choose. They measure general test sets, and your documents, vocabulary and users' wording may behave differently. A small test on your own questions is more reliable.

How many questions do I need to compare embedding models?

Enough to cover each question type that matters to you with several examples. With a small set, treat differences of one or two questions as noise and read the individual failures.

Can I mix vectors from two embedding models in one index?

No. Vectors from different models are not comparable, so queries and documents must be embedded with the same model or a pair designed to work together. Changing model means re-embedding the collection.

Is a larger embedding model always better?

No. A larger model may score higher on general tests but not on your content, and it can cost more and respond more slowly. Choose the cheapest model that is not meaningfully worse on your own test.
