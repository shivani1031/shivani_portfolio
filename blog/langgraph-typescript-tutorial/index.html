LangGraph TypeScript tutorial: your first LangGraph.js graph

To build a first graph in LangGraph.js, install @langchain/langgraph, @langchain/core and zod, describe the shared state with StateSchema, write each node as a function that receives the state and returns a partial update, then connect the nodes with addEdge and addConditionalEdges on a StateGraph. Call compile() and run it with invoke. The complete example below type-checks and runs as written.

What you will build

A small support router. A classify node reads a customer question and decides whether it is about billing. A conditional edge then sends the run to either a billing node or a general node, and both end the graph. Every node also appends its name to a steps list, so you can see the path each run took.

There is no model call yet. A keyword check stands in for the classifier, so you can learn the graph mechanics without an API key and then swap in a model later. If you work in Python instead, the same ideas are covered in the LangGraph tutorial for beginners; this guide is the TypeScript version, using the JavaScript library's own way of defining state.

Step 1: set up the project

In a new folder, install the packages:

npm install @langchain/langgraph @langchain/core zod
npm install --save-dev typescript

This tutorial was checked against @langchain/langgraph 1.7, @langchain/core 1.4 and zod 4, and the code follows the Graph API page of the official LangGraph JavaScript documentation. LangGraph.js has changed how state is declared over time: older tutorials use Annotation.Root, which the package still exports, while the current documentation uses StateSchema. If your installed version differs, check its documentation before copying code from any tutorial.

The sample uses top-level await, so set "type": "module" in package.json and use a tsconfig.json with "module": "NodeNext" and "strict": true. Run it with a TypeScript runner such as tsx, or compile it with tsc first.

Step 2: the complete example

Here is the whole program. It is illustrative: the routing rule is deliberately simple. The sections that follow explain each part.

// Illustrative only. A keyword check stands in for a model call.
import { StateGraph, StateSchema, ReducedValue, START, END } from "@langchain/langgraph";
import type { GraphNode } from "@langchain/langgraph";
import * as z from "zod";

const TicketState = new StateSchema({
  question: z.string(),
  category: z.string().default(""),
  answer: z.string().default(""),
  steps: new ReducedValue(z.array(z.string()).default(() => []), {
    inputSchema: z.string(),
    reducer: (current, step) => [...current, step],
  }),
});

const classify: GraphNode<typeof TicketState> = (state) => {
  const text = state.question.toLowerCase();
  const category = text.includes("refund") || text.includes("invoice") ? "billing" : "general";
  return { category, steps: "classify" };
};

const billing: GraphNode<typeof TicketState> = (state) => ({
  answer: `The billing team will review: ${state.question}`,
  steps: "billing",
});

const general: GraphNode<typeof TicketState> = (state) => ({
  answer: `Here is some general help for: ${state.question}`,
  steps: "general",
});

function routeByCategory(state: typeof TicketState.State): "billing" | "general" {
  return state.category === "billing" ? "billing" : "general";
}

const graph = new StateGraph(TicketState)
  .addNode("classify", classify)
  .addNode("billing", billing)
  .addNode("general", general)
  .addEdge(START, "classify")
  .addConditionalEdges("classify", routeByCategory, ["billing", "general"])
  .addEdge("billing", END)
  .addEdge("general", END)
  .compile();

const first = await graph.invoke({ question: "Where is my refund?" });
console.log(first.category, "|", first.answer);
console.log(first.steps.join(" -> "));

const second = await graph.invoke({ question: "How do I reset my password?" });
console.log(second.category, "|", second.steps.join(" -> "));

Running it prints:

billing | The billing team will review: Where is my refund?
classify -> billing
general | classify -> general

Step 3: understand the state

The state is the shared record that every node reads and updates. StateSchema takes an object whose fields are zod schemas. A plain field such as question: z.string() keeps its latest value: when a node returns a new value, it replaces the old one. Defaults such as z.string().default("") mean a field has a value even before a node sets it, so the caller only has to provide the question.

The steps field is different. It is wrapped in ReducedValue, which pairs the stored type, an array of strings, with a reducer that says how an update is combined with the current value. Here each node returns a single string and the reducer appends it. Because inputSchema is z.string(), TypeScript expects nodes to return a string for steps, not an array, and will flag a mistake at compile time. State design goes much deeper than this, including messages and parallel updates, and is covered in LangGraph state explained.

Step 4: write the nodes

A node is a function that receives the current state and returns an object with only the fields it wants to change. The classify node returns category and a step; it does not repeat question or answer, and it does not modify the state object it was given. LangGraph merges the returned fields into the state, applying a reducer where one is defined.

Typing the nodes as GraphNode<typeof TicketState> gives you checked access to the state fields and checked return values, so a misspelt field name is a compile error rather than a silent no-op. Note that GraphNode is imported with import type: it exists only for the type checker, and runners that strip types need it marked that way. Nodes can also be async, which you will need once they call a model or an API.

Step 5: connect nodes with edges

addEdge(START, "classify") makes classify the entry point, and addEdge("billing", END) ends the run after billing. START and END are special node names imported from the package.

The conditional edge is where routing happens. addConditionalEdges("classify", routeByCategory, ["billing", "general"]) means: after classify runs, call routeByCategory with the updated state and go to the node it names. The third argument lists the possible destinations. Declaring them lets LangGraph draw and check the graph, and the router's return type, a union of the two names, gives you a compile-time check too. You can also pass an object that maps the router's return values to node names, which is handy when the router returns labels such as "yes" and "no".

Keep routers simple and free of side effects: read the state, return a name. If a decision needs a model call, make that call in a node, store the result in state, and let the router read it, exactly as classify does here.

Step 6: compile and invoke

compile() checks the structure, for example that every edge points at a node that exists, and returns a runnable graph. invoke takes the input state and resolves with the final state once the run reaches END. For long runs you can use stream instead to receive updates as each node finishes, which is how you show progress in a user interface.

To keep state between calls, for a chat that continues over several messages, pass a checkpointer such as MemorySaver to compile and give each conversation a thread id in the config. The in-memory saver is for development; production systems use a persistent store.

Step 7: replace the stand-in with a model

To make classify real, make it async, call a chat model with the question and a short instruction listing the allowed categories, and validate the reply before storing it. Ask for a structured response, or check that the returned label is one of your categories and fall back to "general" if it is not. The graph, edges and router stay the same, and that is the main benefit of the design: the control flow is ordinary, testable code, and the model only fills in the decision.

Common mistakes

  • Returning the whole state. Return only what changed. Returning stale copies of other fields can overwrite newer values.
  • Mutating the input. Changing state in place is not how updates are recorded; return them instead.
  • Router names that do not match. A router that returns a name the graph does not know will fail at run time. A union return type catches most of these.
  • Mixing tutorial styles. Combining Annotation.Root snippets with StateSchema code from different versions causes confusing type errors. Pick one style for a project.

Where to go next

Before adding features, write a small test that invokes the graph with a billing question and a general one and checks the steps each run took. Tests like this keep routing changes safe as the graph grows.

Add a third branch, then a node that loops back to classify with a retry limit stored in state. For more graph shapes, including tool calls and approval steps, see LangGraph examples. If you are planning a production workflow, the orchestration with LangGraph page describes what I can help with.

Frequently asked questions

Is LangGraph available for TypeScript?

Yes. LangGraph.js is published on npm as @langchain/langgraph and offers the same core ideas as the Python library: a shared state, nodes, edges, conditional edges, checkpointers and streaming.

Should I use StateSchema or Annotation.Root?

The current LangGraph.js documentation defines state with StateSchema and zod. Annotation.Root is still exported and appears in older tutorials. Use one style consistently within a project.

How does a conditional edge work in LangGraph.js?

After the source node runs, LangGraph calls your routing function with the updated state and moves to the node whose name it returns. You can list the possible destinations or map return values to node names.

Do I need an LLM to use LangGraph.js?

No. Nodes are ordinary functions, so a graph can run with no model at all. That makes it easy to learn and test the control flow first, then add model calls inside nodes.
