RAG chatbot with conversation memory in Python

A Python RAG chatbot handles follow-up questions by rewriting each new message into a standalone search query using recent turns, then retrieving with that query while answering the original message. To make it reliable, keep history to whole turns within a token budget, record which sources each answer used so that "the second one" can be resolved, fall back to the original message when a rewrite fails or looks wrong, and test the rewrite step with its own conversation cases.

Where this fits

How to build a RAG chatbot in Python ends with a simple follow-up step: a chat loop that keeps the last few turns and rewrites each message as a standalone question before retrieving. That is the right starting point. This guide takes that step further, covering the decisions it leaves open: how much history to keep and how to measure it, what to show the rewrite prompt, what to do when the rewrite goes wrong and how to test it.

It deals only with memory inside one conversation. Memory that persists across sessions, such as user preferences, is a different problem with its own risks, covered in agent memory: short-term and long-term state. That guide's advice on trimming and summarising context applies here too; what follows is specific to retrieval.

Why follow-ups break retrieval

Retrieval compares the query with your chunks. A first question such as "What is the refund window for annual plans?" contains the words that matter. A follow-up such as "And for monthly ones?" does not: it has no mention of refunds, so the search finds whatever happens to be closest to "monthly". The model then answers from the wrong passages, often confidently.

There are two common responses. One is to search with the whole conversation, which drags old topics into every query. The other, used here, is to turn the follow-up into a standalone query first. The key separation is that the rewritten query is used for search only. The answer step still receives the user's original message and the conversation, so the reply sounds like a continuation rather than an answer to a question the user never typed.

Step 1: keep a history window, measured in tokens

History has to be limited, because every turn you keep is sent with every request. Counting turns is a crude limit, since one long answer can outweigh ten short exchanges. A better rule is to keep whole turns, newest first, until a token budget is used up:

# Illustrative: keeps whole turns, newest first, within a token budget.
def history_window(turns, budget, count_tokens, max_turns=8):
    kept, used = [], 0
    for turn in reversed(turns[-max_turns:]):
        size = count_tokens(turn["user"]) + count_tokens(turn["assistant"])
        if used + size > budget:
            break
        kept.append(turn)
        used += size
    return list(reversed(kept))

Illustrative sketch. count_tokens stands for the tokeniser of the model you use.

Two details matter. Turns are kept whole, so the model never sees an answer without the question that prompted it. And there is a maximum number of turns as well as a budget, so that a run of very short messages cannot fill the window with stale context. The right budget depends on your model and costs; controlling LLM cost and latency covers how to set it.

The rewrite step needs even less history than the answer step. Resolving "it" or "that one" rarely needs more than the last two or three turns, and a shorter input makes the rewrite cheaper and less likely to pull in an old topic.

Step 2: rewrite with clear rules and a fallback

The rewrite prompt should be explicit about what not to change. Models tend to paraphrase, and a paraphrase that drops an order number or a product code makes the search worse, not better:

# Illustrative: rewrite a follow-up, with checks and a safe fallback.
REWRITE_PROMPT = """You rewrite the user's latest message as one standalone
search query for a document index. Resolve words such as "it", "that"
and "the second one" using the conversation. Keep names, numbers and
codes exactly as written. If the message is already standalone or
changes topic, return it unchanged. Return only the query."""


def format_turns(turns):
    lines = []
    for turn in turns:
        lines.append(f"user: {turn['user']}")
        lines.append(f"assistant: {turn['assistant']}")
        if turn.get("sources"):
            lines.append(f"(sources shown: {', '.join(turn['sources'])})")
    return "\n".join(lines)


def rewrite_query(message, turns, call_llm, max_chars=300):
    if not turns:
        return message, "no_history"
    try:
        query = call_llm(REWRITE_PROMPT, f"{format_turns(turns)}\nuser: {message}").strip()
    except Exception:
        return message, "rewrite_failed"
    if not query or len(query) > max_chars or "\n" in query:
        return message, "rewrite_rejected"
    return query, "rewritten"

Illustrative sketch. call_llm is a placeholder for your model call, taking a system prompt and a user message and returning text.

This version does three things that the simple loop in the earlier guide does not:

  • It shows the sources from earlier turns. When a user says "what about the second one?", the referent is often a document or option the bot listed, not something the user typed. Including the source names gives the rewrite something to resolve against.
  • It handles topic changes. The prompt tells the model to return a standalone message unchanged, so a new question is not merged with the previous topic.
  • It falls back safely. If the call fails, returns nothing, returns several lines or produces something much longer than a query, the original message is used. A poor search is better than an error page.

The function also returns a status, which tells you how often each path is taken. A rising share of rejected rewrites usually means the prompt or model needs attention.

You can skip the rewrite for the first message, as the code does, since there is nothing to resolve. Skipping it for later messages that look standalone is tempting to save a call, but heuristics for that are unreliable: "Is it free?" is short and obviously dependent, while "What about the API?" may or may not be. Unless cost forces it, rewrite every follow-up and let the prompt decide.

Step 3: put the turn together

One chat turn now has a clear order: trim the history, rewrite, retrieve with the rewritten query, generate from the original message, then save and log:

# Illustrative: one turn of the chatbot, logging what was searched.
def chat_turn(message, turns, retrieve, generate, call_llm, count_tokens, log):
    window = history_window(turns, budget=1500, count_tokens=count_tokens)
    query, status = rewrite_query(message, window[-3:], call_llm)
    passages = retrieve(query)
    reply = generate(message, window, passages)
    sources = [p["source"] for p in passages]
    log({"message": message, "query": query, "status": status, "sources": sources})
    turns.append({"user": message, "assistant": reply, "sources": sources})
    return reply

Illustrative sketch. retrieve, generate and log are placeholders for your own pipeline. Run with stub functions, the second message in a test conversation was rewritten and logged as expected.

Each saved turn keeps its sources. That is what the rewrite prompt reads in later turns, and it also lets you show users what an earlier answer was based on.

The log line is the most useful debugging tool in a conversational RAG system. When a follow-up gets a poor answer, compare the message with the query. If the query is wrong, the problem is in the rewrite. If the query is right but the sources are wrong, it is in retrieval. Without the log, both look the same.

Step 4: test the rewrite on its own

Single-question test sets do not exercise memory at all. Add conversation cases: a short history, a follow-up and the terms that a correct standalone query must contain. Checking for required terms rather than an exact string keeps the test stable when the model phrases the query differently:

# Illustrative: conversation test cases check the rewrite, not the answer.
CASES = [
    {
        "turns": [{"user": "What is the refund window for annual plans?",
                   "assistant": "Annual plans can be refunded within 30 days [1].",
                   "sources": ["billing.md"]}],
        "message": "And for monthly ones?",
        "must_contain": ["refund", "monthly"],
    },
    {
        "turns": [{"user": "How do I reset my password?",
                   "assistant": "Use the link on the sign-in page [1].",
                   "sources": ["account.md"]}],
        "message": "What payment methods do you accept?",
        "must_contain": ["payment methods"],
    },
]


def rewrite_failures(call_llm):
    failures = []
    for case in CASES:
        query, _ = rewrite_query(case["message"], case["turns"], call_llm)
        if not all(term in query.lower() for term in case["must_contain"]):
            failures.append((case["message"], query))
    return failures

Illustrative sketch, run with a stub in place of the model.

Cover the patterns your users produce. Useful cases include pronouns ("does it work offline?"), ellipsis ("and in Germany?"), references to listed items ("tell me more about the second one"), corrections ("no, I meant the business plan") and outright topic changes, where the right rewrite is the message unchanged. Run these whenever you change the rewrite prompt or the model behind it, then run your end-to-end checks from how to evaluate a RAG system.

Storing conversations

In a web service, the history lives in a database or cache keyed by conversation, not in a Python list. Decide early how long conversations are kept and who can read them, because users often paste personal details into chat. Keep only what the bot needs, delete it on a schedule and never let one user's history reach another user's prompt. If you summarise long conversations to save tokens, keep the original turns available for debugging, since a summary can drop the detail a follow-up depends on.

Common mistakes

  • Answering the rewritten query instead of the user's message. The reply loses its conversational tone and can answer the wrong question if the rewrite drifted.
  • Sending the whole history to search. Old topics leak into every query.
  • Trimming mid-turn. A reply without its question confuses both the rewrite and the answer.
  • Not logging the rewrite. Retrieval failures and rewrite failures become impossible to tell apart.
  • Testing only first questions. Most memory bugs appear on the second or third turn.

Frequently asked questions

How do I handle follow-up questions in a RAG chatbot?

Rewrite each follow-up into a standalone search query using the last few turns, retrieve with that query, then answer the user's original message with the conversation and retrieved passages. Fall back to the original message if the rewrite fails.

How much conversation history should a RAG chatbot keep?

Keep whole turns, newest first, within a token budget and a maximum number of turns. The rewrite step usually needs only the last two or three turns, while the answer step may use a larger window.

Should the chatbot search with the whole conversation?

Usually not. Searching with the full history pulls old topics into every query. A rewritten standalone query keeps retrieval focused on what the user is asking now.

How do I test conversation memory in a chatbot?

Add conversation cases with a short history, a follow-up and the terms a correct rewritten query must contain. Include pronouns, references to listed items, corrections and topic changes, and log every rewrite in production.
