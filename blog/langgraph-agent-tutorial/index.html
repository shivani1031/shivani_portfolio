LangGraph agent tutorial: build a tool-using agent step by step

To build a tool-using agent in LangGraph, keep a list of messages in the state, add a model node that calls a tool-calling chat model, add a ToolNode that runs the tools it asks for, and add a conditional edge after the model that goes to the tools when the reply contains tool calls and ends otherwise. An ordinary edge from the tools back to the model closes the loop, and a step counter plus the recursion limit stop it running forever.

What you will build

The agent answers a shop customer's question using two tools: one looks up an order's delivery status and one returns the shop's return policy. Asked "Where is order A100, and can I return it?", the model calls the first tool, reads the result, calls the second, and then writes a final answer. That loop of reason, act and observe is what people usually mean by an agent.

This guide assumes you know the basics of a StateGraph: state, nodes, edges and compile. If not, start with the LangGraph tutorial for beginners, which builds a first graph without a model. For other small patterns, such as branches, approval pauses and subgraphs, see LangGraph examples.

The code was checked against LangGraph 1.2 and langchain-core 1.x, and the LangGraph documentation. To make it runnable without an API key, a scripted stub plays the part of the model. Everything else is the real library.

Step 1: the tools

Tools are ordinary Python functions decorated with @tool from langchain_core.tools. The decorator reads the function name, type hints and docstring to build the description the model sees, so write the docstring for the model: say what the tool does and when to use it. Keep tools narrow. Two clear tools are easier for a model to choose between than one tool with many modes.

Tools should return text or simple data, and should fail gracefully. A tool that raises an exception on a missing order id will stop the run; returning "not found" lets the model tell the customer.

Step 2: the state

An agent's state is mainly a conversation. The messages key uses the add_messages reducer, which appends each node's new messages to the list instead of replacing it, so the model always sees the whole exchange: the question, its own tool calls and each tool result. We add one more key, model_calls, to count how many times the model has run.

Step 3: the model node

The model node passes the messages to the chat model and returns its reply. With a real provider you would create the chat model and call bind_tools(tools) on it, which sends the tool descriptions with every request. The reply is an AIMessage. If the model wants to use a tool, the message has a tool_calls list, each with a tool name, arguments and an id. If it is ready to answer, tool_calls is empty and the text is the answer.

The node also increments model_calls. That counter is the basis of our own step limit.

Step 4: the tools node

ToolNode, from langgraph.prebuilt, is a ready-made node that reads the tool calls in the last AI message, runs the matching tools and returns one ToolMessage per call, tagged with the call's id. The model relies on those ids to match results to requests. You could write this node yourself, but ToolNode handles several calls in one message, and its handle_tool_errors option controls whether a tool error becomes a message the model can read or stops the run.

Step 5: the conditional edge and the loop

This is the heart of the agent. After the model node, a routing function looks at the last message:

  • No tool calls: the model has answered, so go to END.
  • Tool calls, but the step limit is reached: go to a small give_up node that returns a polite message.
  • Tool calls: go to the tools node.

Then an ordinary edge runs from the tools node back to the model. That edge is what makes it a loop: the model sees the tool results and decides again. LangGraph also ships tools_condition, a routing function that returns "tools" or the end; it is fine for simple agents, but writing your own lets you add the step limit and other checks in one place.

The complete agent

Illustrative code. It runs as written with the stub; swap StubModel for a real chat model with tools bound and nothing else needs to change.

# Illustrative only. A scripted stub stands in for a tool-calling chat model.
from typing import Annotated
from typing_extensions import TypedDict
from langchain_core.messages import AIMessage, HumanMessage, AnyMessage
from langchain_core.tools import tool
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.prebuilt import ToolNode

@tool
def get_order_status(order_id: str) -> str:
    """Look up the delivery status of an order."""
    return {"A100": "shipped", "A200": "packed"}.get(order_id, "not found")

@tool
def get_return_policy() -> str:
    """Return the shop's return policy."""
    return "Returns accepted within 7 days of delivery."

tools = [get_order_status, get_return_policy]

class StubModel:
    """Placeholder: replace with model.bind_tools(tools) on a real chat model."""
    def __init__(self, script):
        self.script = list(script)
    def invoke(self, messages):
        return self.script.pop(0) if self.script else AIMessage(content="Done.")

model = StubModel([
    AIMessage(content="", tool_calls=[{"name": "get_order_status", "args": {"order_id": "A100"}, "id": "c1"}]),
    AIMessage(content="", tool_calls=[{"name": "get_return_policy", "args": {}, "id": "c2"}]),
    AIMessage(content="Order A100 has shipped. Returns are accepted within 7 days of delivery."),
])

MAX_MODEL_CALLS = 5

class State(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]
    model_calls: int

def call_model(state: State) -> dict:
    reply = model.invoke(state["messages"])
    return {"messages": [reply], "model_calls": state.get("model_calls", 0) + 1}

def route_after_model(state: State) -> str:
    last = state["messages"][-1]
    if not getattr(last, "tool_calls", None):
        return "end"
    if state["model_calls"] >= MAX_MODEL_CALLS:
        return "give_up"
    return "tools"

def give_up(state: State) -> dict:
    return {"messages": [AIMessage(content="I could not finish this within the step limit. A person will follow up.")]}

builder = StateGraph(State)
builder.add_node("model", call_model)
builder.add_node("tools", ToolNode(tools))
builder.add_node("give_up", give_up)
builder.add_edge(START, "model")
builder.add_conditional_edges("model", route_after_model, {"tools": "tools", "give_up": "give_up", "end": END})
builder.add_edge("tools", "model")
builder.add_edge("give_up", END)
agent = builder.compile()

result = agent.invoke(
    {"messages": [HumanMessage(content="Where is order A100, and can I return it?")], "model_calls": 0},
    config={"recursion_limit": 20},
)
for m in result["messages"]:
    print(type(m).__name__, "|", m.content or m.tool_calls)
print("model calls:", result["model_calls"])

Running it prints the question, the first tool call, its result, the second tool call, its result and the final answer, with three model calls in total. Because the stub is scripted, you can see the exact path through the graph, which is also how to unit test routing without paying for model calls.

Step 6: the step limit

A model can loop: calling the same tool again with slightly different arguments, or bouncing between two tools. You want two guards.

The first is your own counter, as above. When model_calls reaches MAX_MODEL_CALLS and the model still wants tools, the graph ends gracefully with a message the user can act on. In a test where the stub always asks for a tool, the run stops after five model calls with the give-up message.

The second is LangGraph's recursion limit, which caps the number of super-steps in one run. Pass it in the config, as a top-level key: config={"recursion_limit": 20}. When it is exceeded, LangGraph raises GraphRecursionError. The documentation gives a high default in recent versions, so do not rely on the default to catch a looping agent; set a value suited to your graph. Each trip round the loop uses two steps, one for the model and one for the tools, so leave room above your own limit. Treat the recursion limit as the hard stop and your counter as the friendly one.

Step 7: test it without a model

Scripted stubs make agent tests cheap and repeatable. Useful cases:

  • A reply with no tool calls ends immediately.
  • A single tool call runs the tool and returns to the model.
  • Several tool calls in one message all get results.
  • A model that never stops asking for tools reaches the give-up node.
  • An unknown order id produces a helpful answer, not an exception.

Then test the real model separately, against a set of realistic questions, checking which tools it chose and whether the final answers were right.

When to use the prebuilt agent instead

If your agent is exactly this loop, you do not have to write it. In LangGraph 1.x, create_react_agent in langgraph.prebuilt still exists but is marked deprecated in favour of create_agent from the langchain package, which builds the same model and tools loop on LangGraph and adds a middleware system. Illustrative, again with a scripted fake model:

# Illustrative only. A scripted fake model stands in for a real chat model.
from langchain.agents import create_agent
from langchain_core.language_models.fake_chat_models import GenericFakeChatModel
from langchain_core.messages import AIMessage
from langchain_core.tools import tool

@tool
def get_return_policy() -> str:
    """Return the shop's return policy."""
    return "Returns accepted within 7 days of delivery."

class FakeToolModel(GenericFakeChatModel):
    def bind_tools(self, tools, **kwargs):
        return self

model = FakeToolModel(messages=iter([
    AIMessage(content="", tool_calls=[{"name": "get_return_policy", "args": {}, "id": "c1"}]),
    AIMessage(content="Returns are accepted within 7 days of delivery."),
]))

agent = create_agent(model, tools=[get_return_policy], system_prompt="Answer shop questions using the tools.")
result = agent.invoke({"messages": [{"role": "user", "content": "Can I return this?"}]}, config={"recursion_limit": 20})
print(result["messages"][-1].content)

Use the prebuilt agent when the standard loop fits and you want less code to maintain. Write the graph yourself when you need control the helper does not give you easily: a custom step limit with its own exit, extra nodes such as a check before a risky tool, routing to different places depending on the tool, or state beyond messages. Many projects start with the prebuilt agent and move to a custom graph when one of those needs appears; because both are LangGraph graphs underneath, the move is gradual rather than a rewrite.

Common mistakes

  • Forgetting add_messages. Without the reducer, each node overwrites the conversation and the model loses its tool results.
  • Not binding tools. If the real model was never given the tools, it cannot produce tool calls and the agent always ends after one step.
  • Missing edge back to the model. Without it, the tools run and the graph stops before the answer is written.
  • Vague tool docstrings. The model chooses tools from their descriptions; unclear ones lead to wrong or repeated calls.
  • Dangerous tools with no check. Tools that send messages, spend money or change records deserve a review step before they run.

Frequently asked questions

How do I build an agent with tools in LangGraph?

Keep messages in the state with the add_messages reducer, add a node that calls a chat model with tools bound, add a ToolNode, route from the model to the tools when the reply has tool calls and to END otherwise, and add an edge from the tools back to the model.

What does ToolNode do in LangGraph?

ToolNode reads the tool calls in the last AI message, runs the matching tools and returns one ToolMessage per call with the call's id, so the model can match each result to its request.

How do I stop a LangGraph agent from looping forever?

Count model calls in the state and route to a give-up node when the count reaches your limit. Also pass recursion_limit in the run config, which makes LangGraph raise GraphRecursionError when the run takes too many steps.

Is create_react_agent deprecated?

In LangGraph 1.x, create_react_agent in langgraph.prebuilt is marked deprecated in favour of create_agent from the langchain package, which builds the same tool-calling loop on LangGraph.

Should I use the prebuilt agent or build my own graph?

Use the prebuilt agent when the standard model and tools loop fits. Build your own graph when you need custom limits, review steps before risky tools, different routes per tool or extra state.
