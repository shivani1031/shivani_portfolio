ChromaDB RAG tutorial: indexing, persistence and filters

To use ChromaDB for RAG in Python, create a PersistentClient pointing at a folder, get or create a collection, and upsert each chunk with an id, its text, its embedding and metadata such as source and date. At question time, call query with the question's embedding, the number of results and an optional where filter on metadata, then pass the returned passages to your language model.

Where ChromaDB fits in a RAG system

Retrieval-augmented generation has two phases. Indexing splits your documents into chunks, embeds them and stores them. Answering embeds each question, finds the closest chunks and asks a model to answer from them. ChromaDB is an open-source vector database that handles the storage and search part of both phases.

It is popular for prototypes and small to medium projects because it can run inside your Python process with no separate server, and save its data to a local folder. It can also run as a client and server when several processes need the same data. If you are still deciding whether you need a dedicated vector database at all, read embeddings and choosing a vector database first.

This tutorial was checked against the ChromaDB documentation and run with the 1.x Python package. The API has changed between major versions, so if your code or an older tutorial disagrees with what follows, check the version you have installed against the current documentation.

Installing and creating a persistent client

Install the package with pip install chromadb. ChromaDB offers an in-memory client, which is handy for tests but forgets everything when the program stops, and a persistent client, which saves to a directory. For RAG you almost always want the persistent one:

  • chromadb.PersistentClient(path="./chroma_store") opens or creates the store in that folder. Always pass the path explicitly, so that you know where the data lives.
  • client.get_or_create_collection(name=...) returns a collection, which is roughly a table of records. Collection names have rules: they must be at least three characters, using letters, numbers, dots, underscores and hyphens.
  • The distance function is set when the collection is created, through its configuration. Cosine distance is a common choice for text embeddings. Decide it up front, because changing it later means recreating the collection.

Indexing and querying: a complete example

The sample below is illustrative and runs as written. To keep it self-contained, a toy embed function stands in for a real embedding model. Replace it with your provider's embedding call or a local model; nothing else needs to change.

# Illustrative only. A toy embedder stands in for a real embedding model.
import hashlib
import chromadb

def embed(texts):
    """Placeholder: replace with a real embedding model."""
    vectors = []
    for text in texts:
        v = [0.0] * 64
        for word in text.lower().split():
            v[int(hashlib.md5(word.encode()).hexdigest(), 16) % 64] += 1.0
        vectors.append(v)
    return vectors

client = chromadb.PersistentClient(path="./chroma_store")
collection = client.get_or_create_collection(
    name="handbook",
    configuration={"hnsw": {"space": "cosine"}},
)

chunks = [
    {"id": "leave-1", "text": "Staff receive annual leave each year, booked through the HR portal.",
     "source": "leave-policy.md", "team": "all", "year": 2026},
    {"id": "leave-2", "text": "Unused annual leave can be carried over only with manager approval.",
     "source": "leave-policy.md", "team": "all", "year": 2026},
    {"id": "exp-1", "text": "Travel expenses must be submitted with receipts within the month.",
     "source": "expenses.md", "team": "finance", "year": 2025},
]

collection.upsert(
    ids=[c["id"] for c in chunks],
    documents=[c["text"] for c in chunks],
    embeddings=embed([c["text"] for c in chunks]),
    metadatas=[{"source": c["source"], "team": c["team"], "year": c["year"]} for c in chunks],
)
print("stored:", collection.count())

def search(question, where=None, k=3):
    result = collection.query(
        query_embeddings=embed([question]),
        n_results=k,
        where=where,
        include=["documents", "metadatas", "distances"],
    )
    # Results are nested per query, so take the first list.
    return list(zip(result["documents"][0], result["metadatas"][0], result["distances"][0]))

for doc, meta, dist in search("can I carry over annual leave"):
    print(round(dist, 3), meta["source"], "|", doc)

for doc, meta, dist in search(
    "annual leave",
    where={"$and": [{"team": {"$in": ["all", "hr"]}}, {"year": {"$gte": 2026}}]},
):
    print("filtered:", meta["source"], meta["year"])

collection.delete(where={"source": "expenses.md"})
print("after delete:", collection.count())

Run it twice and the count stays the same. That is the point of upsert: records with an existing id are updated rather than duplicated, and new ids are inserted. Plain add ignores a record whose id already exists, which can leave stale text in place when a document changes. Deterministic ids, built from the file name and chunk position, make re-indexing safe.

Bring your own embeddings or let ChromaDB embed

If you pass only documents, ChromaDB embeds them with the collection's embedding function, and you can query with query_texts. If you pass your own embeddings, it stores them as given and you query with query_embeddings.

Supplying your own embeddings is usually clearer in a RAG system. You choose the model deliberately, you can reuse the same vectors elsewhere, and you avoid a hidden default that may download a model on first use. Whichever you choose, the rule is the same as in any vector store: questions and chunks must be embedded by the same model, and the vectors must have the same length as everything already in the collection. If you change embedding models, build a new collection rather than mixing vectors. Choosing an embedding model covers how to compare candidates.

Reading query results

Results come back column by column and nested per query. result["documents"][0] is the list of texts for the first question, result["metadatas"][0] the matching metadata and result["distances"][0] their distances, where smaller means closer. The include argument controls which fields are returned; ids are always included.

By default a query returns up to ten results. Set n_results explicitly and tune it against your test questions: too few and you miss the passage that holds the answer, too many and the model has more irrelevant text to wade through. Consider also dropping results above a distance threshold, so that an off-topic question can return nothing and the chatbot can say it does not know.

Metadata filters

Metadata turns a similarity search into a targeted one. The where argument filters on metadata before results are returned, using operators such as $eq, $ne, $gt, $gte, $lt, $lte, $in and $nin, combined with $and and $or. A plain {"source": "leave-policy.md"} is shorthand for an equality match. There is also where_document, which filters on the text itself.

Useful metadata for RAG includes:

  • Source and section. For citations, and for deleting or replacing one document's chunks.
  • Dates or versions. So that superseded policies can be excluded rather than retrieved alongside the current one.
  • Product, region or language. To narrow a search when the user has already told you the context.
  • Access groups. To restrict which chunks a given user can retrieve.

On that last point, a filter only protects data if your application always applies it and builds it from the signed-in user, never from anything the user or the model can change. RAG access control and permissions explains the wider design.

Keep metadata values simple: strings, numbers and booleans. Decide the fields before you index a large collection, because adding a field later means re-indexing the documents that need it.

Keeping the index current

Documents change. A simple, reliable pattern is to treat each source file as the unit of update: when a file changes, delete its chunks with collection.delete(where={"source": name}) and upsert the new ones. This avoids orphaned chunks when a document gets shorter. Record a content hash or modified date for each file, so that a scheduled job can skip anything unchanged.

Back up the persistence folder like any other database, and avoid several processes writing to the same local folder at once. If you need concurrent writers or several application servers, run ChromaDB in client and server mode instead.

When to move beyond ChromaDB

ChromaDB is a good fit when you want a quick start, a single application and data that fits comfortably on one machine. You might look elsewhere when your data already lives in PostgreSQL and you want vectors next to it, when you need hybrid keyword and vector search tuned to your domain, or when operational needs such as replication dominate. pgvector vs dedicated vector databases compares those routes.

Because the retrieval step sits behind one small function in the example above, switching later is mostly a matter of reimplementing that function and re-indexing. Keeping that boundary clean is worth more than picking the perfect database on day one.

Frequently asked questions

Is ChromaDB good for RAG?

Yes, for many projects. It is quick to start with, can run inside a Python process, saves to disk with a persistent client and supports metadata filters. Larger or more operationally demanding systems may suit another vector database.

How do I make ChromaDB persist data?

Use chromadb.PersistentClient with a path to a folder. Collections and records are saved there and are available again the next time you open a client with the same path.

What is the difference between add and upsert in ChromaDB?

Add inserts new records and ignores a record whose id already exists. Upsert inserts new records and updates existing ones, which makes re-indexing changed documents safe when ids are deterministic.

How do I filter ChromaDB results by metadata?

Pass a where argument to query or get, for example a source equal to one file name, or an $and of conditions using operators such as $in and $gte. Use where_document to filter on the text itself.

Can I use my own embeddings with ChromaDB?

Yes. Pass embeddings when you add or upsert records and query with query_embeddings. The vectors must come from the same model and have the same length as the rest of the collection.
