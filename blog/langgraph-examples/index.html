LangGraph examples: five small patterns you can run

These five LangGraph examples cover the patterns most workflows are built from: a straight sequence, a branch, a loop with a limit, a pause for human approval and a subgraph. Each runs locally with plain functions standing in for model calls, and each comes with a note on when the pattern earns its place.

How to use these examples

Each example is complete: copy it into a file, install LangGraph with pip install -U langgraph and run it. No API key is needed, because every place where a model would normally be called uses an ordinary Python function instead. That keeps the focus on the graph itself, which is where these patterns differ.

All the samples were run against LangGraph 1.2.20. The core calls they use, StateGraph, add_node, add_edge, add_conditional_edges and compile, have been stable for some time, but check the documentation for the version you install.

This page is a set of patterns rather than a course. If you have never built a graph, start with the LangGraph tutorial for beginners, which explains state, nodes and edges step by step. For design advice on a larger workflow, read building an orchestrator with LangGraph.

1. A linear chain

The simplest graph runs a fixed sequence of steps. Here one node tidies some text and the next summarises it.

from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class State(TypedDict):
    text: str
    cleaned: str
    summary: str

def clean(state):
    return {"cleaned": " ".join(state["text"].split())}

def summarise(state):
    # Stand-in for a model call.
    return {"summary": state["cleaned"][:40]}

builder = StateGraph(State)
builder.add_node("clean", clean)
builder.add_node("summarise", summarise)
builder.add_edge(START, "clean")
builder.add_edge("clean", "summarise")
builder.add_edge("summarise", END)
graph = builder.compile()

print(graph.invoke({"text": "  Refunds are   accepted within 30 days.  "}))

Illustrative example. The summarise node stands in for a model call.

When to use it. Honestly, not often on its own. Two or three steps in a fixed order are usually clearer as plain function calls. A linear graph becomes worthwhile when you expect to add branches later, or when you want LangGraph's checkpointing, streaming or tracing for each step. It is also a useful skeleton: most of the other patterns start from it.

2. A branch on a classification

A conditional edge calls a routing function after a node finishes and sends the run to whichever node it names. Here a message is labelled and then handled by one of two nodes.

from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class State(TypedDict):
    message: str
    label: str
    reply: str

def classify(state):
    # Stand-in for a model; anything unexpected falls back to "other".
    text = state["message"].lower()
    label = "billing" if "invoice" in text else "other"
    return {"label": label}

def billing(state):
    return {"reply": "Routing to the billing answer."}

def other(state):
    return {"reply": "Routing to the general answer."}

def route(state):
    return state["label"]

builder = StateGraph(State)
builder.add_node("classify", classify)
builder.add_node("billing", billing)
builder.add_node("other", other)
builder.add_edge(START, "classify")
builder.add_conditional_edges("classify", route, {"billing": "billing", "other": "other"})
builder.add_edge("billing", END)
builder.add_edge("other", END)
graph = builder.compile()

print(graph.invoke({"message": "Where is my invoice?"})["reply"])
print(graph.invoke({"message": "Do you ship abroad?"})["reply"])

Illustrative example. The keyword check stands in for a model that classifies the message.

The third argument to add_conditional_edges maps each value the router can return to a node. Passing it is optional, but it documents the possible paths and lets LangGraph draw the graph correctly.

When to use it. Use a branch when different kinds of input need different handling, for example billing questions going to an account lookup while general questions go to document search. Keep the judgement in a node, write a validated label into the state, and keep the router a plain lookup. A model that returns an unexpected label should land on a safe default rather than an error.

3. A loop with a limit

Graphs can contain cycles, which is one of the main reasons to use LangGraph. This example retries a search with a broader query until it finds something or runs out of attempts.

from typing import TypedDict
from langgraph.graph import StateGraph, START, END

MAX_TRIES = 3

class State(TypedDict):
    query: str
    results: list[str]
    tries: int

def search(state):
    # Stand-in search that finds nothing until the query is broadened.
    found = ["doc-7"] if state["query"].endswith("*") else []
    return {"results": found, "tries": state["tries"] + 1}

def broaden(state):
    return {"query": state["query"] + "*"}

def route(state):
    if state["results"]:
        return "done"
    if state["tries"] >= MAX_TRIES:
        return "give_up"
    return "retry"

builder = StateGraph(State)
builder.add_node("search", search)
builder.add_node("broaden", broaden)
builder.add_edge(START, "search")
builder.add_conditional_edges(
    "search", route, {"done": END, "give_up": END, "retry": "broaden"}
)
builder.add_edge("broaden", "search")
graph = builder.compile()

print(graph.invoke({"query": "warranty", "results": [], "tries": 0}))

Illustrative example. The search function is a stub that succeeds only after the query is broadened.

Notice that the limit is part of the state and the routing function, not left to the framework. LangGraph also has a recursion limit that raises GraphRecursionError when a run takes too many steps, but that is a backstop. Your own counter lets the graph finish cleanly, and it gives you a field to test and log.

When to use it. Loops suit work that can be checked and retried: a search that returned nothing, a draft that failed validation, or structured output that did not parse. They are a poor fit when there is no reliable check, because the loop will simply repeat the same mistake at extra cost. Decide in advance what happens when the limit is reached, whether that is a fallback answer, a message to the user or a handover to a person.

4. A pause for human approval

Some steps should not happen without a person agreeing, such as sending an email or issuing a refund. LangGraph's interrupt function pauses a run inside a node and returns a value to the caller. The run continues when you invoke the graph again with Command(resume=...) and the same thread ID.

from typing import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.types import interrupt, Command

class State(TypedDict):
    draft: str
    approved: bool
    sent: bool

def write_draft(state):
    return {"draft": "Your refund has been approved."}

def review(state):
    decision = interrupt({"draft": state["draft"], "question": "Send this reply?"})
    return {"approved": decision == "yes"}

def send(state):
    # A real send should be idempotent, because a resumed node can run again.
    return {"sent": state["approved"]}

builder = StateGraph(State)
builder.add_node("write_draft", write_draft)
builder.add_node("review", review)
builder.add_node("send", send)
builder.add_edge(START, "write_draft")
builder.add_edge("write_draft", "review")
builder.add_edge("review", "send")
builder.add_edge("send", END)
graph = builder.compile(checkpointer=InMemorySaver())

config = {"configurable": {"thread_id": "ticket-42"}}
first = graph.invoke({"draft": "", "approved": False, "sent": False}, config)
print(first["__interrupt__"][0].value)

final = graph.invoke(Command(resume="yes"), config)
print(final)

Illustrative example. Nothing is actually sent; the send node only records the decision.

Three details from the LangGraph reference are worth knowing. An interrupt needs a checkpointer, because the paused state must be saved somewhere. When the run resumes, the interrupted node starts again from its beginning, so any code before the interrupt call runs twice. And the in-memory checkpointer used here is lost when the process stops, so production systems need a durable one.

When to use it. Use it for actions that are costly, irreversible or visible to customers, and for decisions where policy requires a named person. Do not gate everything, or reviewers will start approving without reading. The guide to human-in-the-loop approval for AI agents covers what to gate and how to design the review step.

5. A subgraph

A compiled graph can be added to another graph as a node. Here a small draft-and-check flow is built once and used as a single step in a parent workflow.

from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class State(TypedDict):
    question: str
    answer: str
    checked: bool

def draft(state):
    return {"answer": f"Draft answer to: {state['question']}"}

def check(state):
    return {"checked": len(state["answer"]) > 0}

sub = StateGraph(State)
sub.add_node("draft", draft)
sub.add_node("check", check)
sub.add_edge(START, "draft")
sub.add_edge("draft", "check")
sub.add_edge("check", END)
answer_flow = sub.compile()

def log_request(state):
    return {}

parent = StateGraph(State)
parent.add_node("log_request", log_request)
parent.add_node("answer_flow", answer_flow)
parent.add_edge(START, "log_request")
parent.add_edge("log_request", "answer_flow")
parent.add_edge("answer_flow", END)
graph = parent.compile()

print(graph.invoke({"question": "Can I change my plan?", "answer": "", "checked": False}))

Illustrative example. Both graphs share one state type, which is the simplest arrangement.

Because parent and subgraph share the same state keys, the subgraph reads and writes the parent's fields directly. When the two need different state, you call the subgraph from inside an ordinary node and translate the fields in and out yourself.

When to use it. Subgraphs help when a group of steps forms its own unit, is reused in more than one place, or is owned and tested by a different person. They add a boundary to reason about, so a graph with a handful of nodes rarely needs one. Routing into a subgraph by tool name, and handing control back to the parent, are covered in named tool routing in LangGraph.

Choosing between the patterns

Real workflows combine these patterns. A support assistant might branch on the type of question, loop on a draft-and-check step and pause for approval before sending. A useful way to decide is to ask a question of each step:

  • Does it always lead to the same next step? Use a normal edge.
  • Does the next step depend on the result? Use a conditional edge with a validated field in the state.
  • Can the result be checked and improved? Use a loop, with a counter and a planned exit.
  • Should a person decide before it happens? Use an interrupt with a durable checkpointer.
  • Is it a self-contained group of steps? Consider a subgraph.

If a model needs to decide which of several workers runs next, again and again, you have a supervisor or orchestrator pattern. That is a combination of a branch and a loop, and it is covered with a full example in building an orchestrator with LangGraph.

Testing patterns without a model

Each example above already runs without a model, and that is a habit worth keeping in real projects. Replace model calls with stubs that return fixed values, then run the graph once for every path: each branch, the loop that succeeds, the loop that hits its limit, and the approval that is refused as well as the one that is granted. Routing functions are ordinary Python, so they can be unit tested on their own by building a state and checking the name they return.

Once the paths behave as designed, swap the stubs for real model calls and evaluate complete runs against realistic inputs, looking at the path each run took as well as its final output.

Common mistakes with these patterns

  • Missing initial values. A node that reads state["tries"] fails if the run started without that key. Set every field a node reads in the initial input.
  • Lists that overwrite each other. By default a node's update replaces a field. If several nodes add to a list, give the field a reducer such as operator.add.
  • Side effects before an interrupt. Because the node restarts on resume, an email sent before the interrupt call would be sent again. Put side effects after approval, ideally in a separate node.
  • Routers that do too much. A routing function that calls a model is hard to test and hard to trace. Make the decision in a node and route on the stored result.

Frequently asked questions

Do these LangGraph examples need an API key?

No. Every place where a model would normally be called uses an ordinary Python function, so the examples run locally after installing LangGraph. You add a model later by replacing those functions.

What is the difference between a loop limit and the recursion limit?

A loop limit is a counter you keep in the state and check in a routing function, so the graph exits through a path you designed. The recursion limit is a framework safeguard that raises an error when a run takes too many steps.

Why does my node run twice after an interrupt?

When a run resumes, LangGraph restarts the interrupted node from its beginning, so code before the interrupt call runs again. Keep side effects after the approval, ideally in a separate node.

When should I use a subgraph instead of more nodes?

Use a subgraph when a group of steps forms its own unit, is reused in several places or is tested separately. For a small graph, extra nodes in one graph are usually easier to follow.
