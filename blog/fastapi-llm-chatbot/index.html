FastAPI LLM chatbot: models, streaming, conversation IDs and tests

To build an LLM chatbot API with FastAPI, define Pydantic request and response models, accept an optional conversation_id and load the history for it in a dependency, call the model inside a timeout, and return either a JSON reply or a stream of Server-Sent Events. Map model failures to clear status codes before streaming starts and to an error event afterwards, then test every path with TestClient and a stubbed model.

What this guide adds

Serving an LLM app with FastAPI covers the service around a model: project structure, shared clients, async behaviour and concurrency limits. Streaming LLM responses to a web UI covers the browser side of a stream. This guide is the piece in between: one small, complete chatbot API with the decisions that are specific to chat, and tests that run without a model or network.

The code was run with FastAPI 0.141 and Python 3.12, and the FastAPI details were checked against the official documentation. The streaming example uses FastAPI's built-in Server-Sent Events support, which the documentation says was added in version 0.135.0, so older projects need to upgrade or fall back to StreamingResponse.

Design the request and response first

A chat endpoint needs very little input: the user's message and, for a continuing conversation, its ID. Keep it that way. Do not accept the full history or a system prompt from the client, because anything the client sends can be edited, and a client-supplied history lets a user rewrite what the assistant said earlier.

  • Constrain the message. Field(min_length=1, max_length=4000) rejects empty and very long messages with a 422 before you pay for a model call.
  • Make the conversation ID optional. No ID means a new conversation; the server creates one and returns it. Generate IDs on the server, for example with uuid4, so they cannot be guessed.
  • Return a typed response. A response_model documents the reply in the OpenAPI schema, which helps whoever builds the frontend.

The complete API

The sample below is illustrative. A fake_model generator stands in for your provider's streaming client and has two trigger words, slow and boom, so that the tests can exercise timeouts and errors.

# Illustrative only. fake_model stands in for a real LLM client.
import asyncio
import uuid
from collections.abc import AsyncIterable, AsyncIterator
from typing import Annotated, Literal

from fastapi import Depends, FastAPI, HTTPException
from fastapi.sse import EventSourceResponse, ServerSentEvent
from pydantic import BaseModel, Field

MODEL_TIMEOUT_SECONDS = 30
MAX_TURNS = 20


class ChatRequest(BaseModel):
    message: str = Field(min_length=1, max_length=4000)
    conversation_id: str | None = None


class ChatResponse(BaseModel):
    conversation_id: str
    reply: str


class Turn(BaseModel):
    role: Literal["user", "assistant"]
    content: str


# In memory for the example; use a database or Redis in production.
conversations: dict[str, list[Turn]] = {}


async def fake_model(history: list[Turn]) -> AsyncIterator[str]:
    """Placeholder: replace with your provider's streaming call."""
    last = history[-1].content
    if last == "slow":
        await asyncio.sleep(60)
    if last == "boom":
        raise RuntimeError("provider error")
    for word in f"You said: {last}".split():
        await asyncio.sleep(0)
        yield word + " "


def load_history(req: ChatRequest) -> tuple[str, list[Turn]]:
    """Runs as a dependency, before any response starts, so a 404 is still possible."""
    if req.conversation_id is None:
        return str(uuid.uuid4()), [Turn(role="user", content=req.message)]
    if req.conversation_id not in conversations:
        raise HTTPException(status_code=404, detail="Unknown conversation_id")
    history = conversations[req.conversation_id]
    return req.conversation_id, history + [Turn(role="user", content=req.message)]


Conversation = Annotated[tuple[str, list[Turn]], Depends(load_history)]


def save(conversation_id: str, history: list[Turn]) -> None:
    conversations[conversation_id] = history[-MAX_TURNS:]


app = FastAPI()


@app.post("/chat", response_model=ChatResponse)
async def chat(conv: Conversation) -> ChatResponse:
    conv_id, history = conv
    try:
        async with asyncio.timeout(MODEL_TIMEOUT_SECONDS):
            reply = "".join([c async for c in fake_model(history)]).strip()
    except TimeoutError:
        raise HTTPException(status_code=504, detail="The model took too long to reply")
    except RuntimeError:
        raise HTTPException(status_code=502, detail="The model provider returned an error")
    save(conv_id, history + [Turn(role="assistant", content=reply)])
    return ChatResponse(conversation_id=conv_id, reply=reply)


@app.post("/chat/stream", response_class=EventSourceResponse)
async def chat_stream(conv: Conversation) -> AsyncIterable[ServerSentEvent]:
    conv_id, history = conv
    yield ServerSentEvent(data={"conversation_id": conv_id}, event="start")
    parts: list[str] = []
    try:
        async with asyncio.timeout(MODEL_TIMEOUT_SECONDS):
            async for chunk in fake_model(history):
                parts.append(chunk)
                yield ServerSentEvent(data={"text": chunk}, event="token")
    except (TimeoutError, RuntimeError):
        # The status code has already been sent, so report the failure as an event.
        yield ServerSentEvent(data={"message": "The reply could not be completed"}, event="error")
        return
    save(conv_id, history + [Turn(role="assistant", content="".join(parts).strip())])
    yield ServerSentEvent(data={"conversation_id": conv_id}, event="done")

Conversation IDs and history

The load_history dependency does three jobs: it creates an ID for a new conversation, rejects an unknown ID with a 404, and appends the new user message. In a real service it should also check that the conversation belongs to the signed-in user, otherwise anyone holding an ID can read or continue someone else's chat.

Running this as a dependency matters for streaming. FastAPI resolves dependencies before the endpoint runs, so the 404 is returned normally. When tested, raising the same exception inside the streaming generator did not produce a 404, because the response had already begun.

The dictionary is for the example only. Store conversations in a database or Redis so they survive restarts and work across several server processes. Save the assistant's reply only after it completes, and trim or summarise long histories so the prompt stays within the model's limits; RAG chatbot with conversation memory discusses the trade-offs.

Streaming with Server-Sent Events

With response_class=EventSourceResponse, an endpoint can yield items and FastAPI sends each as an SSE event. Yielding ServerSentEvent objects lets you name events, and the data field is encoded as JSON. According to the documentation, FastAPI also sends a keep-alive comment when the stream is idle and sets headers that discourage caching and proxy buffering.

A small, explicit event vocabulary keeps the client simple: start carries the conversation ID, token carries text, and the stream ends with exactly one of done or error. SSE works with POST as well as GET, but the browser's built-in EventSource only makes GET requests, so a POST stream is usually read with fetch on the frontend.

Timeouts and errors

Every model call needs a limit. asyncio.timeout, available from Python 3.11, cancels the call if it runs too long. Set your provider client's own timeout as well, since it can also stop waiting on the network.

Choose status codes that tell the client what happened without exposing internals:

  • 422 for an invalid request, which FastAPI produces from the Pydantic model.
  • 404 for an unknown or inaccessible conversation.
  • 502 when the model provider returns an error.
  • 504 when the model does not answer in time.

Once streaming has started, the status code has already been sent as 200. The only way to report a failure is in the stream, which is why the streaming endpoint catches the same errors and yields an error event. Log the underlying exception on the server with the conversation ID, and keep the client message generic. Catch the specific exceptions your provider's SDK raises rather than RuntimeError, which only fits the stub.

Replacing the stub with a real model

Only fake_model needs to change when you connect a provider, as long as the replacement is an async generator that yields text. Inside it, build the provider's message list from the stored turns, and add the system prompt on the server so users cannot change it. Create the provider client once at start-up rather than per request, as the serving guide describes, and reuse it.

Map the provider's errors deliberately. A rate-limit error from the provider is different from a bad request caused by an over-long history, and both differ from an outage. Decide which ones are worth a single retry before the first token is sent, which become a 502 or 503, and which point to a bug in your own code. Never retry after tokens have reached the client, or the user will see the reply start twice.

Finally, keep the stub. With a real model behind the same interface, the tests below still run against the stub, quickly and for free, while a separate, smaller set of checks exercises the real provider.

A minimal test suite

FastAPI's TestClient calls the app in process, so these tests need no server and no network. They cover a continuing conversation, bad input, an unknown ID, the provider error, the timeout and a complete stream. client.stream reads the streaming response as it arrives.

# Illustrative only. test_chat.py, run with: pytest test_chat.py
from fastapi.testclient import TestClient

import main

client = TestClient(main.app)


def test_conversation_keeps_its_id():
    first = client.post("/chat", json={"message": "hello"})
    assert first.status_code == 200
    conv_id = first.json()["conversation_id"]
    second = client.post("/chat", json={"message": "again", "conversation_id": conv_id})
    assert second.json() == {"conversation_id": conv_id, "reply": "You said: again"}


def test_bad_input_and_unknown_conversation():
    assert client.post("/chat", json={"message": ""}).status_code == 422
    r = client.post("/chat", json={"message": "hi", "conversation_id": "nope"})
    assert r.status_code == 404


def test_provider_error_and_timeout(monkeypatch):
    assert client.post("/chat", json={"message": "boom"}).status_code == 502
    monkeypatch.setattr(main, "MODEL_TIMEOUT_SECONDS", 0.05)
    assert client.post("/chat", json={"message": "slow"}).status_code == 504


def test_stream_sends_tokens_then_done():
    with client.stream("POST", "/chat/stream", json={"message": "hi there"}) as r:
        assert r.status_code == 200
        body = "".join(r.iter_text())
    assert "event: token" in body
    assert "event: done" in body
    assert "event: error" not in body

The timeout test shortens the limit with pytest's monkeypatch instead of waiting. In a larger app, swap the model through a dependency and app.dependency_overrides, which keeps tests independent of module globals.

Before you deploy

Add authentication and rate limits per user, cap the number of concurrent model calls, and check that any proxy in front of the app passes streams through without buffering. Record the time to the first token and the total time for each request, so slow replies can be traced to the model or to your own code. Frequently asked questions

Can FastAPI stream LLM responses?

Yes. From version 0.135.0 FastAPI has built-in Server-Sent Events: set response_class=EventSourceResponse and yield items or ServerSentEvent objects. Older versions can return a StreamingResponse from a generator.

How do I keep conversation history in a FastAPI chatbot?

Return a server-generated conversation ID with the first reply, have the client send it back with each message, and load and save the history for that ID in a database or Redis, checking that it belongs to the user.

How should a FastAPI chatbot handle model timeouts?

Wrap the model call in a timeout and return a 504 for a normal request. If streaming has already started, send an error event instead, because the status code has already been sent.

How do I test a FastAPI chatbot without calling the model?

Replace the model with a stub, through a dependency override or a patched function, and call the endpoints with TestClient. The stub can also trigger timeouts and errors on purpose.

Should the client send the whole chat history to the API?

Usually not. A client-supplied history can be altered. Store the history on the server and accept only the new message and the conversation ID.
