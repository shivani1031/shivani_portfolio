GLiNER vs LLM for named entity recognition

For named entity recognition with your own entity types and no training data, start with a compact zero-shot model such as GLiNER when you need fast, cheap extraction of short, well-named entities over a lot of text, and prompt a large language model when the entities need judgement, context or normalisation, or when you also want other structured fields. There is no single best model for NER: the right choice depends on your labels, your volume and where the data may be processed, so test both on a sample of your own documents.

Two ways to get entities without training

Traditional NER models are trained on a fixed set of labels, such as person, organisation and location. If you need "policy number" or "drug dosage", you would once have labelled thousands of examples and trained a model. Two newer approaches remove that step.

GLiNER is a family of compact open models designed for zero-shot NER. You give it the text and a list of label names at run time, and it scores spans of the text against each label. The project describes it as lightweight enough to run on CPUs and consumer hardware, and the models are published on Hugging Face in several sizes.

A prompted LLM is a general model that you instruct to extract entities, usually returning JSON. With no examples this is zero-shot; with a handful of worked examples in the prompt it is few-shot. The broader picture of extraction with LLMs, including schemas and validation, is in named entity recognition and data extraction with LLMs. This guide focuses on the choice between the two.

How they differ in practice

  • Output. GLiNER returns spans that come from the input text, so an entity cannot be invented. An LLM writes its answer, so it can paraphrase, normalise or occasionally produce an entity that is not there.
  • Cost and speed. A small model running on your own machine has no per-call fee and suits large batches. An LLM call costs per token and is usually slower, especially for long documents.
  • Where data goes. GLiNER can run entirely on your own infrastructure. A hosted LLM means sending text to a provider, unless you run an open model yourself.
  • Judgement. An LLM can follow instructions such as "only the buyer, not the seller" or "convert dates to ISO format". A span model finds mentions; it does not reason about roles.
  • Labels. Both accept label names at run time. GLiNER is sensitive to how a label is worded, so "organisation" and "company name" may give different results. An LLM can take a description of each label as well as a name.

Running GLiNER

The package installs with pip install gliner. The sample below follows the usage shown in the official repository and model card: load a model with from_pretrained, then call predict_entities with the text, the labels and a threshold. It is illustrative, and it downloads model weights from Hugging Face the first time it runs.

# Illustrative only. Downloads a model from Hugging Face on first run.
from gliner import GLiNER

model = GLiNER.from_pretrained("gliner-community/gliner_small-v2.5")

text = "Priya Nair from Acme Analytics signed the renewal on 12 June 2026."
labels = ["person", "organisation", "date", "product"]

entities = model.predict_entities(text, labels, threshold=0.5)
for entity in entities:
    print(entity["text"], "=>", entity["label"])

The threshold sets how confident the model must be before a span is returned. Raise it for fewer, surer entities; lower it if you are missing mentions. Text longer than the model's input limit needs splitting into chunks first, and labels work best as short, ordinary nouns. Check each model's card for its licence before using it commercially, because terms differ between models.

Prompting an LLM: zero-shot and few-shot

With an LLM, the prompt is the model's whole specification. A good extraction prompt names the labels, describes any that are ambiguous, fixes the output format and tells the model to copy entities exactly as they appear. Adding two or three examples, few-shot prompting, usually helps most with unusual labels and edge cases, such as whether a job title belongs with a person.

The sample below is illustrative. A stub stands in for the model so it runs without an API key, and it deliberately returns one entity that is not in the text, to show why the check at the end matters.

# Illustrative only. fake_llm stands in for a real chat model call.
import json

LABELS = ["person", "organisation", "date", "product"]

PROMPT = """Extract entities of these types: {labels}.
Return JSON: {{"entities": [{{"text": "...", "label": "..."}}]}}.
Copy each entity exactly as it appears in the text. If none, return an empty list.

Example
Text: Ravi joined Infotech Ltd on 3 March.
Output: {{"entities": [{{"text": "Ravi", "label": "person"}},
 {{"text": "Infotech Ltd", "label": "organisation"}}, {{"text": "3 March", "label": "date"}}]}}

Text: {text}
Output:"""


def fake_llm(prompt: str) -> str:
    """Placeholder: replace with your model provider's call, ideally with JSON mode."""
    return json.dumps({"entities": [
        {"text": "Priya Nair", "label": "person"},
        {"text": "Acme Analytics", "label": "organisation"},
        {"text": "12 June 2026", "label": "date"},
        {"text": "Acme Cloud Pro", "label": "product"},   # not in the text: a hallucination
    ]})


def extract(text: str) -> list[dict]:
    raw = fake_llm(PROMPT.format(labels=", ".join(LABELS), text=text))
    entities = json.loads(raw).get("entities", [])
    kept = []
    for ent in entities:
        start = text.find(ent.get("text", ""))
        if ent.get("label") in LABELS and ent.get("text") and start != -1:
            kept.append({**ent, "start": start, "end": start + len(ent["text"])})
    return kept


doc = "Priya Nair from Acme Analytics signed the renewal on 12 June 2026."
for ent in extract(doc):
    print(ent["label"], "|", ent["text"], ent["start"], ent["end"])

Running it prints the person, organisation and date with their character offsets and drops the invented product. That last step is the important habit: never trust an LLM's entities until you have confirmed they exist in the source and their labels are in your list. If you use your provider's structured output or JSON mode, you also avoid most formatting failures; structured output from LLMs explains the options.

What is the best model for named entity recognition?

There is no single answer, and anyone who names one without asking about your data is guessing. For standard labels in well-supported languages, a trained model from a library such as spaCy may already do the job. For custom labels with no training data, a zero-shot model like GLiNER and a prompted LLM are the two main candidates. If you have labelled data and a stable set of labels, fine-tuning a compact model often gives the most consistent results.

The same trade-off appears across NLP tasks, and text classification with LLMs vs traditional NLP walks through it for classification. The pattern is similar: LLMs are quick to start and flexible; smaller models are cheaper and more predictable at volume.

Comparing them on your own data

A fair comparison needs a small test set, not impressions from a demo:

  1. Pick a sample of real documents, including awkward ones, and mark the correct entities by hand.
  2. Run both approaches with the same labels. Tune the GLiNER threshold and the LLM prompt on part of the set, and keep the rest for the final check.
  3. Measure precision and recall per label, not just overall, because one difficult label often hides behind a good average.
  4. Record time and cost per document at the volume you expect.
  5. Read the errors. Missed entities, wrong boundaries and wrong labels each point to a different fix.

Decide in advance what counts as a match. If the reference says "Acme Analytics Pvt Ltd" and the model returns "Acme Analytics", is that right? Exact-match scoring will say no; for many uses a partial match is fine.

Combining the two

You do not have to pick one. A common pattern is to run the compact model on everything and send only the hard cases to an LLM, such as low-confidence spans or documents where a required entity is missing. Another is to let GLiNER find candidate spans and ask an LLM to decide roles, for example which of two organisations is the supplier. Both keep most of the cost and latency of the small model while using the LLM's judgement where it pays off.

Choosing

Lean towards GLiNER when volume is high, data must stay on your own servers, the entities are short mentions with clear names, and you want outputs that always come from the text. Lean towards an LLM when labels need explanation, entities need normalising, you are also extracting other fields from the same document, or volume is modest enough that per-call cost does not matter. Either way, validate the output and measure on your own documents before you rely on it.

Frequently asked questions

What is the best model for named entity recognition?

It depends on your labels and data. Trained models suit standard labels, zero-shot models such as GLiNER suit custom labels at volume, and prompted LLMs suit entities that need judgement or normalisation. Test candidates on your own documents.

Is GLiNER better than an LLM for NER?

Neither is better in every case. GLiNER is small, can run locally and returns spans from the text. An LLM follows richer instructions and can normalise values, but costs more per call and its output must be checked against the text.

What is the difference between zero-shot and few-shot NER?

In zero-shot NER the model gets only the label names or descriptions. In few-shot NER the prompt also includes a few worked examples, which usually helps with unusual labels and edge cases.

Can GLiNER run without a GPU?

Yes. The project describes GLiNER as lightweight enough to run on CPUs and consumer hardware. Larger models and long documents will run more slowly, so measure speed on your own machine.
